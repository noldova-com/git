# Security model

**Scope:** Who may write to a person's repositories through the Git modules, each write's risk and permission, what a write refuses even with permission, how the person's own git runs, what failures and logs never carry, and which changes count as risky in review.

The organization's security standard, `https://github.com/noldova-com/.github/blob/main/standards/SECURITY.md`, applies here in full.
The packages, parts, methods and limits are in [ARCHITECTURE.md](ARCHITECTURE.md).

## Threats

The modules act in the person's repositories and on their accounts, for the person and for agents.
They defend against:

- **An agent that oversteps:** it writes without the person's approval, pushes somewhere the person didn't see, forces, resets or rewrites history.
- **A caller that isn't the person:** another client of the runtime calls a write method as if the person had clicked.
- **A request that changes under the person:** what runs differs from what the card showed, because the branch, the staged files or the remote moved before the answer.
- **A repository that steers the module:** its file names, commit messages or git's output tell the module or the agent to act, or its configuration runs a command the person never chose to run.
- **A leak:** a URL's name, password or token, or a host key's trust, that reaches a message, a log, a card or a remote.

The modules trust the app's main process, the person's answers to permission requests and the person's own git and its configuration, as the person's own `git` in a terminal would.
They trust nothing that comes from a repository's contents, from git's output, from an agent's arguments or from a remote.
Every answer from Azure DevOps is read only up to 32 MiB, and Microsoft's sign-in token answer, a few KB, only up to 1 MiB: a longer one fails its read, or the sign-in, as `Unavailable`, and is never parsed in part or logged, so no answer from the host can fill the runtime's memory.

**The trust boundary:** a person's click, or a write the person allowed, is the person's own git command, so the repository's hooks and filters run as they would from the person's terminal, and every request an agent's write raises names each hook that will run, a checked-out submodule's too when a switch recurses into it, and a stage's or switch's request each filter that will run whose command the repository's own configuration gives.
A read runs nothing the repository names, so no read starts a command from the repository's configuration: before each status, diff and prediction, the module switches off the clean and process filters the repository's own configuration names, as ARCHITECTURE.md says. Without Git LFS's clean filter, git calls an LFS file modified whenever its stat moved, as after a checkout, so the status read checks each such file itself, never by running the filter: when `git check-attr` says `filter=lfs` and the index holds an LFS pointer, it counts the file unmodified if its SHA-256 and size are the pointer's, hashing again only once the file's size, mtime or ctime moves. It asks `git check-attr` and `git cat-file` once a read, with the paths on their input, so it checks any number of files, and it hashes up to 1 GiB a read: a file past that stays as git reported it, and the status counts it in `uncheckedLfsFiles`, so the window says some LFS files weren't checked rather than showing a wrong state silently; the next read checks it.
A prediction of a merge, cherry-pick or revert answers `Unavailable` rather than run a merge driver that the repository's own configuration names.

## Who may write

The write methods, `git.stage`, `git.unstage`, `git.discard`, `git.createBranch`, `git.switchBranch`, `git.commit`, `git.push`, `git.pull`, `git.cherryPick`, `git.revert`, `git.merge`, `git.createBranchAt`, `git.renameBranch`, `git.deleteBranch`, `git.createTag`, `git.deleteTag`, `git.stageLines`, `git.unstageLines`, `git.amend`, `git.undo`, `git.reset`, `git.undoCommit`, `git.forcePush`, `git.resolveConflict`, `git.continueOperation`, `git.abortOperation`, `git.fetch`, `git.stash` and `git.rebase`, are the person's own clicks in the Git view, and `git.undo` is also the person's own Edit → Undo or Mod+Z in the window, which undoes only the open repository's newest write.
Each answers `Unauthorized` to any caller but the app's main process acting for a window, before it reads its parameters, so the command line, another client or a client with no window can't write as the person.
The check rests on the client name the connection's handshake gives, which Noldova Desktop checks for the main process; it keeps out other clients, not other programs that run as the same person.
A person's own click never asks.

An agent writes only through its tools, `git_stage`, `git_unstage`, `git_create_branch`, `git_switch_branch`, `git_commit`, `git_push` and `git_pull`, which act only in the repository that holds the session's `git.folder` binding, never one an argument names; each of its writes that asks raises Noldova Desktop's permission request through the tool's call before anything runs, and marks its point of no return only after the person's answer and the stale checks, just before git starts.

A branch counts as the session's only when no remote-tracking branch of that name existed, as of the last fetch, when the session made it, so a push never offers "Always allow" for someone else's branch.
Noldova Desktop remembers an "Always allow" by the action, the subject and the conversation, so the push request that offers it names the session in its subject: the remembered answer holds only for that session's later pushes of the branch, and never for another session's in the same conversation.
A Low- or Medium-risk request that offers it gives its words, "Always allow in this repository", since a host leaves out an Always option that comes without them. For the other writes the grant holds for the repository; for a push it holds only for that session's later pushes of that branch to that remote, as above.
Noldova Desktop refuses a High-risk request that gives words and offers Always allow, and that rule stays as it is. So only the push of the session's own branch, at Medium risk, offers Always allow, with the words "Always allow in this repository"; every other push is High risk and offers only Allow once and Deny.
The module remembers which branches each session made only while it runs, and a restart starts new sessions, so after a restart every push asks.

## What a write refuses

- **A request that moved:** each write names the status it is based on by its fingerprint. A status that moved since fails as `Stale`, and after the person allows a request the module reads the status and the request again, one write at a time per repository, and runs nothing when either changed. An agent's request is read again even when it asked nothing, so a write that came to need an ask while it waited runs nothing.
- **A request it can't show exactly:** a request whose details pass Noldova Desktop's limits, such as a commit of more files than the card holds, or a commit whose status was cut short, is refused before it is raised.
- **History:** only the person's own clicks change past commits: amend, reset, undo the last commit, force push and undo; no agent tool offers them yet. A force push is always `--force-with-lease` against the commit the person saw. A push sends only the current branch's commit as the status read it, through a refspec the module builds from that commit and the checked branch name, never with `+`, with no tags and no submodules, so a commit that reached the branch after the request was shown is never sent; it publishes a branch without an upstream under its own name and sets that as its upstream.
- **A push it would lose:** a push behind its upstream, as of the last fetch, is refused as `PushBehind`, and so is a push the remote refuses because its branch has commits the local one doesn't; any other refusal of the remote, such as a hook's or a protected branch's, fails as `PushRejected`.
- **A switch during a merge, rebase, cherry-pick or revert**, and a commit with nothing staged or with conflicts left.
- **A conflict resolution that isn't done:** a resolved text with a marker line left, a choice the conflict's kind doesn't offer, and a continue while a file is unmerged or still has a marker line, staged or not.
- **A held lock or an unsafe repository:** a write git refuses because `index.lock` is held, as its error says, is reported as `IndexLocked` and the lock is never deleted, and a repository git calls unsafe fails as `NotRepository` with the Git code `UnsafeRepository`, naming the folder, and is never added to `safe.directory`.
- **A host key:** the module never trusts a host key; an unknown or changed key fails as `HostKeyUnknown` with git's output, and the person checks and trusts it from their own terminal.

## The person's own git

The module runs the person's `git` through Noldova Desktop's `startProcessAsync`, never a shell, with no terminal prompt and `GCM_INTERACTIVE=never`; a read sets `GIT_LITERAL_PATHSPECS=1` and a write marks each path `:(literal)`, so no path is read as a pattern and a write's hooks don't inherit the setting; arguments that name a path come after `--`, and a revision after `--end-of-options`.
Every run, a write too, passes `-c core.fsmonitor=false`, so a command that a repository's own configuration names as its fsmonitor never runs from the module.
Checking a commit's signature, which a view does, passes `-c` for `gpg.program`, `gpg.openpgp.program`, `gpg.ssh.program`, `gpg.x509.program`, `gpg.ssh.defaultKeyCommand`, `gpg.ssh.allowedSignersFile` and `gpg.minTrustLevel`, each set to the person's own global or system value or git's default, so a program the repository's own configuration names never runs, and the repository never decides whose signature verifies.
Starting a watch writes one empty file into the repository's git folder, `noldova-watch-<random>`, and one into `refs/heads`, `noldova-watch-<random>.lock`, a name git never reads as a branch, but none into a reftable repository's `reftable` folder, and removes both as soon as the watch reports them; the module removes no other file there, except such files an earlier run left behind.
Everything else is the person's own git behaviour, as a commit or push from their terminal would be:

- hooks run: `pre-commit`, `prepare-commit-msg`, `commit-msg` and `post-commit` on a commit, `post-checkout` on a switch or a new branch, `pre-push` on a push, `post-index-change` on each write that writes the index, and `reference-transaction` on each that moves a ref; the module never passes `--no-verify`, and each request an agent's write raises names the hooks of these that the repository has;
- the person's identity, signing settings and credential helper apply, from the home the module passes on as `HOME`, or on Windows `HOMEDRIVE` and `HOMEPATH`, and a remote that asks for a name or password with no helper to answer fails as `CredentialsNeeded`;
- a filter driver the repository names, such as Git LFS's, runs when a write stores or checks out a file, since switching it off would store or check out something else: a stage without LFS's clean filter would commit the whole file instead of its pointer; an agent's stage or switch names the repository's own filters in its request.

So a repository's hooks and filters run code the repository names, with the person's rights, as they do for the person's own git; the module adds no sandbox around them, and turns none of them off for a write, since a hook such as Git LFS's is part of how the repository works.

## What failures and logs never carry

- A URL's name, password or token, also when git prints one: a push request shows the push URL without them, and every failure message, and the git output an agent tool's failure carries, strips them.
- The command log, which `git.commandLog` answers to a window, keeps each write's git command line, so it holds what the person wrote, such as a commit message, but never a URL's name, password or token, nor a control character; it lives only in the runtime's memory, and no agent tool reads it.
- git's output comes with a failure as untrusted text, marked as the repository's, never as the module's words or instructions.
- A file name, commit subject or author in a request or a message has each control character replaced before the module shows it.
- A GitHub Enterprise token: only a window may give it, through `git-github.signInWithToken`; the module sends it only to the server it was given for, under `https://<server>/api/v3`, keeps it in the module's secrets like a GitHub account's, and never logs it or answers it to a window; a failure names the server and the scope, never the token. github.com's reads and tools never take an Enterprise account's token.
- A host's token: the Azure DevOps sign-in refuses a payload without a token or an organization's name in a fixed sentence that never repeats it, and logs only the account it signed in as; the token goes only to `dev.azure.com` and `vssps.dev.azure.com` under the organization it was given for.
- The sign-in with Microsoft's code, verifier, access token and refresh token: none is logged or answered to a window; the code and verifier go only to `login.microsoftonline.com`, the refresh token only there and to the module's secrets, and the access token only to `dev.azure.com` and `vssps.dev.azure.com` under the organization the person named.

## Risky changes

A change to any of these is risky in review:

- who may call a write method, or the check of the caller;
- the risk table, which writes ask, what a request shows and what "Always allow" holds for;
- the stale checks, or what a write runs between the person's answer and git;
- the arguments a write passes to git, above all a push's refspec, its remote and its options;
- which of the person's git settings, hooks or filters run, or are turned off;
- what failures, cards and logs carry from git's output or a remote's URL;
- a new write;
- which modules can read the GitHub tokens through `git-github.access`, which account it answers for a repository, or what it answers;
- how the GitHub module chooses the account for a repository, what that check sends, or how the picks and the other accounts' secrets are kept;
- how the Azure DevOps module chooses the account for a repository or a reference's read or write, or how its picks and the other accounts' secrets are kept;
- which hosts the GitHub or GitHub Enterprise tokens go to, who may give the module an Enterprise token, whether GitHub's sign-in and API follow a redirect, how much of an answer they read, or what the avatar read sends, follows or takes;
- who may give the Azure DevOps module a token, which hosts the token goes to, whether a request follows a redirect with it, or how it is kept;
- the sign-in with Microsoft: its client, authority or scopes, what the loopback listener binds to, accepts or answers, how its state and PKCE verifier are made, or how its refresh token is kept and renewed;
- what `git-azure-devops.readAuthorAvatar` or `git-azure-devops.readPersonAvatar` sends to Azure DevOps or takes, or which work item icons the module takes;
- what `git.avatar` sends to Gravatar, follows or takes.

## What the sign-in with Microsoft sends and keeps

Only the person starts it, from the Azure DevOps account's dialog on Settings → Accounts and hosts; `git-azure-devops.startSignIn` answers `Unauthorized` to any other caller.
It is Microsoft Entra's authorization-code flow with PKCE as a public client: the module holds no client secret, and a code taken on its way back is useless without the verifier, which never leaves the module until it is redeemed.
The person's browser gets only the authorize address on `login.microsoftonline.com/organizations`: the client id, the redirect `http://127.0.0.1:{port}`, a random state, the S256 challenge and the scopes `vso.code`, `vso.code_write`, `vso.work_write` and `vso.graph` on Azure DevOps with `offline_access`; `vso.graph` is there for Azure DevOps' pictures of authors and people, which `git-azure-devops.readAuthorAvatar` and `git-azure-devops.readPersonAvatar` read, and the reviewer search and its identity ids, and `vso.code_write` for the replies, thread states and votes above, though it also allows pushing to the person's repositories, which no method of the module does.
The listener binds `127.0.0.1` only, on a port the system picks, and the redirect names `127.0.0.1` too, not `localhost`, so the browser never tries `::1`, where another local process could listen on the same port.
It takes one GET on `/` whose state matches in constant time and that carries a code or an error, answers anything else, a target that isn't an address too, with a 404, answers the match with a plain-text page with no script and `no-store`, and closes; it closes too on Cancel, sign-out, the app quitting, or after five minutes, which ends the sign-in as `Expired`.
The code and verifier go only to Microsoft's token endpoint; the access token goes only to `dev.azure.com` and `vssps.dev.azure.com` under the organization the person named; the refresh token goes only to Microsoft's token endpoint and to the module's secrets, kept as the personal access token is but as `git-azure-devops.microsoftSignIn`, so a build that knows only the token's `git-azure-devops.signIn` never sends it to Azure DevOps as a token, and each renewal keeps the new one; keeping either kind removes the other's, and sign-out tries to remove both even when one removal fails.
A renewal Microsoft refuses as needing a new sign-in (`invalid_grant`, `interaction_required` or `consent_required`) signs out with `Expired`; any other failure keeps the sign-in and logs only the failure.
A renewal Microsoft refuses only because the person never allowed `vso.code_write`, as a sign-in made before replies and votes was, asks once more with the earlier scopes, without `vso.code_write`; the sign-in it keeps then sends no reply, thread state or vote, each failing as `Unauthorized` with a sentence that asks the person to sign in again, and the log says so once per renewal.
A reply, thread state or vote Azure DevOps refuses as forbidden fails as the token's missing Code write, unless Azure DevOps names a missing repository permission, which fails as `Unavailable` and says to ask an administrator; a forbidden read stays a refusal.
No code, state, verifier, token or query string is logged; a window gets the authorize address, with its state, port and challenge, in the waiting sign-in and on `git-azure-devops.signInChanged`, and never the verifier or the code.

## What GitHub's sign-in and API follow and read

The sign-in's requests go only to `github.com` and the token's only to `api.github.com`.
The sign-in follows no redirect: a redirect is refused like any other answer that isn't a success, so no device code goes on to another host.
A read on the API follows one redirect by hand, only when its target stays on `https://api.github.com`, the same host and scheme, without a user or password, as GitHub's 301 for a renamed or transferred repository; a post follows none, so its body goes nowhere else.
Any other redirect fails as `Unavailable`, saying the repository moved and to update the remote, so the token never goes on to another host.
An answer is read a chunk at a time, at most 64 KiB for the sign-in's and 8 MiB for the API's; a longer one is refused, as `SignInAnswerTooLargeException` or `Unavailable`, and the rest of it let go of.

## Which GitHub account reads a repository

The GitHub module keeps several accounts: the first in `git-github.signIn`, each other in `git-github.account<id>`, and the index `git-github.accounts` with each other account's id, host and login and the person's picks, each a repository's host and path with the account picked for it.
The index is local data in the module's secrets; nothing in it is logged or sent.
Each read, tool and other module's access takes the account for the repository it acts on: the signed-in account whose login is the user name in the remote's address, which the module reads from the person's Git configuration in the main process only, for a window's folder or an agent session's, holds in memory and never keeps, logs, answers or shows a window, which learns only whether it chose the account; another module's access takes it once a window or tool has read it for that repository; else the person's pick if that account is signed in, else the only signed-in account, else the first signed-in account that can read the repository, else the first.
For that check the module asks `api.github.com` for the repository, by its path, with each signed-in token in turn, until one reads it; it asks once a session for each repository, and again after any account changes.
A token GitHub refuses as unauthorized is reported to its account; a token refused another way, such as a 403, moves on to the next account, and the choice isn't kept.
Picks match a repository's host and path without case.
An added account that signs in as a login another account already holds keeps no token: the module forgets it and ends that account signed out with `AlreadyKept`, so no login is held twice.
`git-github.access` answers `accessAsync` with the first account's token and login, and `accessForAsync` with the token and login of the account chosen for the repository it names, so another module's runtime part gets only the account the GitHub module would read that repository with; it refuses a repository on any host but github.com, so no GitHub Enterprise token reaches another module yet.
A GitHub Enterprise account's token goes only to its own server's API, `https://<server>/api/v3`, and a github.com account's only to `api.github.com`; an answer's link to another origin is never followed with it.
The API's answer cache is kept apart for each token, so one account never gets an answer read with another's token, and the cache of a token no account holds any more is let go of.

## Which Azure DevOps account reads a repository

The Azure DevOps module keeps several accounts, each signed in to one organization: the first in `git-azure-devops.signIn` or `git-azure-devops.microsoftSignIn`, each other in `git-azure-devops.account<id>` or `git-azure-devops.microsoftAccount<id>`, and the index `git-azure-devops.accounts` with each other account's id, organization and login and the person's picks, each a repository's host and path with the account picked for it.
The index is local data in the module's secrets; nothing in it is logged or sent, and a token goes only to the organization its account signed in to.
A read for a repository takes the person's pick while that account is signed in to the repository's organization, else the first account signed in there; no request is made to choose.
A read or write through a pull request's reference, such as a vote, reply, thread state, completion, abandonment or added reviewer, goes as the account the reference's repository reads with, once the module has read one of that repository's pull requests by its address, in its list, its heads, a branch's or a commit's pull request, its commit comments or its review requests; for one it hasn't, it goes as the account last picked in the organization while that one is signed in there, else as the first account signed in there. So a pick for one repository never makes another repository's vote go as a different account than its reads.
Picks match a repository's host and path without case.
An account that signs in as a login another account already holds in the same organization keeps no token: the module forgets it and ends that account signed out with `AlreadyKept`, so no login is held twice in an organization.

## What reaches GitHub for a picture

`git-github.readAuthorAvatar` reads a commit author's picture for the Git view.
For a GitHub no-reply email it asks only GitHub's avatar host, for the account the email names, without the token.
Otherwise, signed in, it asks GitHub's API for the commit, with the token, and then the avatar host for the account GitHub links to it, as the reference author's avatar is read: the window gets the picture only as a data address.
It asks nothing for a repository off github.com, and signed out it asks only for no-reply emails.

## What reaches Azure DevOps for a picture

`git-azure-devops.readAuthorAvatar` reads a commit author's picture for the Git view only while signed in, and only for a repository in the organization of the sign-in.
It sends the author's email, trimmed and in lower case, with the sign-in, to that organization's Graph on `vssps.dev.azure.com` to find the user whose email it is, then asks Graph for that user's picture; it follows no redirect.
It takes only a PNG, JPEG, GIF or WebP image of at most 64 KiB, by the image's own first bytes, answers none for a picture Azure DevOps made itself, so Gravatar's can show, and the window gets the picture only as a data address.
It keeps the answers for the last 500 emails while the app runs.

A work item type's icon comes from Azure DevOps' `workitemicons` endpoint on `dev.azure.com`, with the token, once for each type and account: the module takes only an answer of at most 64 KiB whose text starts as SVG, whatever type Azure DevOps names, answers none otherwise, and logs why.
The window draws it only as an image from a `data:` address, where SVG runs no script and loads nothing, never as markup it inserts.

`git-azure-devops.readPersonAvatar` reads, the same way and under the same limits, the picture of a person the Azure DevOps pages show, such as a pull request's author or reviewer, a comment's author, or a work item's assignee, by the sign-in name Azure DevOps gives for them.
It sends that name to Graph only when it reads as an email, trimmed and in lower case, and shares the answers it keeps with the authors' by organization and email; for any other name it asks nothing and answers none.

## What reaches Gravatar

To show an author's picture when the repository's host has none, the runtime's `git.avatar` asks `https://www.gravatar.com/avatar/` for the SHA-256 of the author's email, trimmed and in lower case, at 64 pixels and with `d=404`, so an email with no picture answers 404 rather than a stand-in.
It sends no token, cookie or other header than `Accept` and `User-Agent`, follows no redirect, takes only a PNG, JPEG, GIF or WebP image of up to 64 KiB within 5 seconds, and gives the window the image only as a base64 data address.
Gravatar learns the hash of each author's email the person views and the person's address; the hash of a common email can be guessed.
It keeps the last 500 answers, a picture or none, and asks again after a failure, which it logs without the email or its hash.
The setting Settings → Git → Show Gravatar pictures (`git.gravatar`), on by default, turns this off: while it's off, `git.avatar` answers no picture and asks Gravatar nothing. Pictures a window already shows stay until it's opened again.

A risky change comes with tests that drive its failure path: a caller that isn't the main process, a status or request that moved, each denied, expired or withdrawn answer, each refusal above, and a request over Noldova Desktop's limits.

## The journal and undo

- **What it records:** each write the module runs, for a person or an agent, records the local branches, tags and HEAD before and after it, for staging the index's tree, for a discard the checkpoint taken before it with the discarded paths, and for a stash the stash's commit, read with `rev-parse` after it, in a journal kept by the repository's common Git folder while the module runs, the last 50 writes.
  It reads them with `for-each-ref`, `symbolic-ref` and `rev-parse`, and the index's tree with `write-tree`, which adds the tree's objects to the repository and changes nothing else; it records nothing of a write that failed or whose refs can't be read after it.
- **What an undo puts back:** the index's tree with `read-tree`, the refs with one `update-ref --stdin` transaction that checks each ref still names what the write left, the current branch with `reset --mixed` or `reset --keep`, or HEAD with `switch` back to the branch or commit the write left, as the write's own undo mode says.
  A stash's undo runs `git stash pop --index --quiet`, only while the stash is still the newest, HEAD is still the commit it was made on, the folder has no changes and nothing, an ignored file or a link whose target is gone included, is at or in the way of a path of the untracked files it holds, listed with `git ls-tree -r --name-only -z` of its third parent when `git rev-parse --verify --quiet` finds one, so the pop applies cleanly or not at all; otherwise it refuses as `Stale` and the stash stays. A listing that fails, or that is cut at its output limit, counts as in the way: the undo refuses as `Stale` and the stash stays.
  A discard's undo asks the checkpoints module to preview restoring only the discarded paths from the checkpoint, then to carry out that plan, which replaces those paths' current content; every other path, the index and the refs stay as they are.
  It never resets hard and never drops a local change: `reset --keep` and `switch` refuse where one would be overwritten.
- **What an undo refuses:** an entry that is no longer in the journal, a write that can't be undone, such as a push or a discard taken without a checkpoint, a discard's undo once the checkpoints module is off, and any entry where the checked-out branch, a ref it moved or the index has moved since the write, as `Stale`; it also refuses while a merge, rebase, cherry-pick or revert is in progress or a file has conflicts.
  The worktrees of one repository share its journal, which also keeps the git folder of the worktree each write ran in: an undo that acts on HEAD, the index, the files or the stash runs only in that worktree and refuses in any other as `Refused`, since two worktrees detached at the same commit look alike to the check of what moved; an undo of refs alone, such as a branch made at a commit, runs from any of them, but refuses as `Refused`, naming the worktree, to delete or move a branch another worktree has checked out, as `git update-ref` doesn't look at other worktrees the way `git branch` does.
  An undone entry leaves the journal, so it can't be undone twice.
