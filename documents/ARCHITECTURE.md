# Architecture

**Scope:** The repository's modules, their packages and parts, how they build, pack and release, and the boundaries their code keeps.

## The modules

The repository holds a set of modules for apps on [Noldova Desktop](https://github.com/noldova-com/desktop), each in its own folders in `src`, as [README.md](../README.md) describes.
Today it holds three: the local Git module, its main module, in `src/noldova.git`, the GitHub module in `src/noldova.git.github` and the Azure DevOps module in `src/noldova.git.azure-devops`, each with its protocol and window part in sibling folders named after it, such as `src/noldova.git.protocol` and `src/noldova.git.window`.
Beside them is the hosting protocol, `src/noldova.git.hosting.protocol`, a package that every host module implements and that isn't a module itself.
A host module added later, for another service, joins them as folders beside them, a module a person can turn off.
A host module depends on the local module and the hosting protocol, never on another host.
The local window part takes the hosting protocol too: its models are shared by the local window part, which draws a pull request page's Commits, Files and Conflicts tabs the same way for every host, and the host modules, and the local module still names no host.

The repository automation reads the modules from one list, which `scripts/models/repository-module.ts` builds from the names in `scripts/resources.ts`: each module's name, which is its folder under `src`, and its package name, from which its protocol's and window part's folders and names follow, and, apart from them, the packages the modules share, by folder and package name.
The package layout, the build, the packer, the declaration check and the test type-check go through every module in the list and every shared package; the import scan takes every package whose name starts with the main module's package name and a dot, `@noldova/git.`, as one of the repository's own.

## The package

Each module ships as three packages, and the hosting protocol as one, all at the local Git module's version, with every pin exact and every peer a range, as below; a peer on another of the organization's packages runs from a version it was built and tested with to the next minor below 1.0, as the organization's TypeScript standard (`standards/stacks/TYPESCRIPT.md`, "Dependencies") says.
Noldova Desktop's catalog still requires an exact peer on a package outside its shared packages, so an app that includes the GitHub module builds only with the Noldova Desktop release that accepts a ranged peer, noldova-com/desktop#111.
Each module accepts a range of Noldova Desktop versions, its `module.json`'s `noldovaDesktop`, as Noldova Desktop's `documents/MODULES.md` ("Noldova Desktop versions") says: from the version it builds and tests against, the root `package.json`'s exact pin, to the next minor below 1.0, or the next major from 1.0.
  0.0.1 is the lowest since it is the first Noldova Desktop published on npm, as the `@noldova/desktop.*` packages.
Its package's peers on Noldova Desktop's packages take that range, and context's a range of the same form; the window packages' peers are written at packing: context's packages as each window project's `peerDependencies` declares them, from the root's pin to the next minor, since each of context's packages pins its siblings exactly and an exact dependency would install a second copy; Noldova Desktop's packages taking `noldovaDesktop`; the kit, and the editor's `@noldova/code.editor` packages, the range from each pin to the next minor; Angular's the range from its pin to the next major, as that document's "Angular versions" says, and the repository's own packages the range from the module's version to the next minor, such as `>=0.0.1 <0.1.0`, which the shared pipelines' archive step requires of a package that takes its siblings as peers.

Each part, and the hosting protocol, keeps its source in `src/` and its tests in `tests/`, mirroring `src/`, and declares its entry point `src/api/index.ts` in a handwritten `src/api/index.d.ts`.
A module's parts import its protocol, and a host module's parts the hosting protocol, by package name.
Every package under `src` is one of the root's npm workspaces, so the repository has one install, the root's `package-lock.json`, whose `node_modules` links each package to its source.
Context's core package defines fixed properties on `Object`, so a second copy throws when it loads; the build checks that the install holds one, and each window part's `vitest.config.ts` has Vite pre-bundle the three context packages, so its tests load one.
The window part's own code may import them as values, such as context's `Exception` and `JsonException`: the published window packages take `@noldova/context.exceptions` and `@noldova/context.json` as peers, so an app holds one copy, and its tests pre-bundle them, so they load one too.
The Git view's branch icon is Primer Octicons' `git-branch` (MIT); the window part's `THIRD-PARTY-NOTICES.md` carries its license and ships in its package.
Each manifest exports `.ts` sources.
The build maps each export to its compiled `.js` and to the handwritten declarations beside it.

`npm run build` (`scripts/build.ts`) runs `npm ci`, with a 10-minute deadline, when there is no install or `package-lock.json` is newer than the last install's `node_modules/.package-lock.json`, then checks, with npm's own tree listing, that the repository's tree holds one copy of `@angular/cdk`, which the UI kit shares, and one of `@noldova/context.core`, which context's packages, Noldova Desktop's and the protocols share, and stops, naming each copy, when it holds more of either, or none ([TESTING.md](TESTING.md#the-pull-request-checks)). `scripts/models/single-copy-package.ts` names both packages.
The modules' packages aren't npm workspaces: the root `package.json` holds every development dependency, the window parts' Angular, interface kit and browser test packages among them.
The build then removes `_packages` and `_build/compiled` and builds each package in turn, the hosting protocol first, then each module's protocol, window part and own package: it compiles a protocol or runtime part into `_build/compiled/<folder>`, such as `_build/compiled/noldova.git.protocol`, packs the package into `_packages`, building it in `_build/packages`, and installs every archive packed so far into the repository's `node_modules` with `npm install --no-save` (`scripts/services/package-install.ts`), as an outside user installs them; each install also names the version `node_modules` holds of each `@noldova/` package the root `package.json` pins, since an install otherwise takes the lockfile's version back, so a build after the Module range workflow's install keeps the newest Noldova Desktop in range and the versions it pins, or, for a package the lockfile resolves to a local archive (`file:`), that archive, since the registry doesn't hold it.
So each part, each window part's build and every test import the packed packages built before them, never their sources, and no configuration maps a package's name to a path.
Each manifest records the commit as its `gitHead` only when the folder is a git checkout without uncommitted changes; otherwise the build says why it records none.
A window part's build imports its module's protocol, the hosting protocol, and the protocol and window part of each module its module depends on (`RepositoryModule`'s `dependencies`: the GitHub module's are the Git module's) as installed from their archives, and takes the window package's dependencies and peers from what the compiled part's scripts and declarations import, at the versions the window part's `package.json` pins, and the repository's own packages at the module's version. It refuses to pack a part that imports a package the manifest doesn't pin. The packages of a module its module depends on are peers from the module's version to the next minor, optional as the app's are, not dependencies, so an app holds one Git window part, whose host rows the Git view reads.

`.github/workflows/release-npm.yml` releases the packages to npm through the organization's shared npm release, v2.51.2, with npm's trusted publishing and provenance, so no token is stored: each package's trusted publisher on npm is this repository's `release-npm.yml` in the `release` environment.
A member starts it by hand with a version and a commit on main, and the `release` environment's reviewer approves the publication.
The pull request that changes the version writes that version's section in [CHANGELOG.md](../CHANGELOG.md), from the pull requests merged since the previous version, and no other pull request edits the file.
A release never deletes a published version.
After the release, its dependents job calls the organization's shared `update-dependents.yml`, v2.51.2, with the version and the commit, in the `version-updates` environment, which holds the version-updates App's key and deploys from `main` only; each repository the App's installation includes that pins this module's packages exactly at an older version, such as the app, gets a pull request that moves the pins and refreshes its lock files, as the shared workflow's README says.
The shared release reads the version from `version.json`, checks that the commit is on main and holds that version, and tags the commit first; it then runs `npm ci` and `npm run build`, checks the archives in `_packages` against the build's `--list-copies`, and publishes them.
A build or publish that fails keeps its tag, so the same version can be released again from the same commit, but a fixed commit needs a new version.
`npm run build` refuses to pack when `version.json`, the root `package.json` or another module's `module.json` holds a version other than the local module's `module.json`, so a version change moves them all, with every package's manifest.

## The parts

| Part | Where it runs | What it does today |
|---|---|---|
| Runtime | The app's main process, activated by Noldova Desktop | Activates and deactivates; the local module's registers `git.status`, `git.diff`, `git.branches`, `git.log`, `git.worktrees`, `git.pullHooks`, `git.watch` and `git.unwatch`, the writes `git.stage`, `git.unstage`, `git.createBranch`, `git.switchBranch`, `git.commit`, `git.push` and `git.pull`, and declares `git.changed`, as "The local runtime part" says, and offers its agent tools, as "Agent tools" says, and the GitHub module's signs in to GitHub, as "Signing in to GitHub" says. |
| Window | Each window, activated by Noldova Desktop | Activates, reconnects while active, and deactivates. The local module's part registers the Git view, `git.view`, in the right dock, in its first group at order 20, where a new layout opens it; the GitHub module's registers no view yet. |

- **Node's API:** the runtime parts run in the app's main process on the Node.js that Electron embeds, 24.22.0 in Noldova Desktop 0.0.9's Electron 44.9.1, so they call only what that Node has. The build type-checks them against `@types/node` 26 and the tests run on Node 26.13.1, so a call only Node 26 has passes both, and a review keeps it out.

The local module's runtime part reads and writes a repository through the person's own `git`, and the agent tools reach it through Noldova Desktop's permission requests.
Its window part shows the Git view of one folder, which the app provides through `GitFolder.provide`; the view refuses a folder that isn't an absolute path of at most 4096 characters and logs why.
`GitViewOptions` holds what an app chooses about the module's look: `showsBranch` turns the branch card off, and `showsAiFeatures`, off by default, shows the AI features, Suggest on the commit message, Explain in a commit's detail and Tidy up for review on the rebase screen; while it is off none of them is drawn, disabled or not, and their rows close up.
A repository's document in front, such as its history, conflicts or rebase, puts its folder ahead of a folder an app shows through `GitFolder.show` and of the provided one; while a document that shows no repository is in front, such as a pull request or a work item, the views keep the repository of the document that was in front last, as long as it is open, unless an app shows a folder.
The view reads the folder's status, branches and diffs through the runtime's `git.*` methods, watches the folder while it shows it and reads the status again on each `git.changed` event; a watch the runtime refuses shows a notice that changes aren't followed, with Check again to watch and read again, except a folder that isn't a repository, which the view already says and which it watches and reads again each time the window takes the focus, so it shows a repository `git init` made there; and sends every write with the status's fingerprint; a write the runtime refuses as `Stale` reads the status again and keeps what the person typed.
The view shows as a failure only the window's own failures of a request, a `WindowException`, and an answer it can't read; any other error, a defect of the view's own, is passed on to Angular's `ErrorHandler`.
It shows the branch card with Push or Publish branch, a host row, a merge or rebase in progress, the Conflicts, Staged and Changes groups with each file's diff inline under its row, and the commit card; `NotRepository`, a folder the person's account may not read (`FolderUnreadable`), git missing or too old, and a folder the app's folder provider can't read each show their own empty state, the last with the provider's message.
When a control that holds the focus goes as it is used, such as a file's Stage, Stage all, N more or a banner's Dismiss in the view, and Sign in, Cancel, Sign out, Try again or Open the page again in the GitHub part's setting and host row, `FocusKeeper`, which the Git window exports and the GitHub part takes from it, moves the focus to the control now at its place in the nearest container that survives, waiting for one while a spinner stands in, and when that control is shown only while its row holds the focus, focusing the row's control before it first, so the focus never falls to the page.
A host module adds its row through `GitHostRows.provide`: the first row whose `claims` accepts the remote renders its component with the folder, branch, head and remote, and a remote no row claims shows one plain line naming it.
A host module gives the commit box a message prefix, such as a work item's id, through `GitCommitPrefixes.provide`: the first host whose `prefixFor` answers other than `null` for the folder and branch fills an empty message, a prefix still untouched follows the branch, and a host whose answer throws is logged through its own context and skipped.
A host module adds the links it knows through `GitLinkReferences.provide`: the commit detail passes the repository's source to its message's Markdown view, which draws a link the source knows as the item's chip; a commit's subject and the history's, the rebase's, the pull requests' and the workspace's rows draw a reference they write the same way, with `GitReferenceText`, as the kit's `a[nol-link-reference-chip]` and a work item's `nol-link-reference-work-item-state` after it, and a plain link while its host has no look for it; a pull request's number that links its whole row, as in the pull requests' rows and the commit's pull request card, draws its chip the same way, and its click goes on to the row; a click on any link, or on one its chip's card activates, opens it through the window, unless a provider's optional `opens(folder, url, injector)` answers true for it, as for an address only that host module handles; the injector is the window's, so the host can open a kit dialog over it.
With two hosts the first that knows a link draws it.
A host module adds rows to the repository panel through `GitRepositoryLinks.provide`: for the current remote, each host answers its `GitRepositoryLink` rows, which show right under Changes and History with their look, and a click runs the row's `open`; a row whose `isActive` says its page is the active document is selected in place of Changes or History; a host answers none for a remote it doesn't claim.
A host module adds its account through `GitHostAccounts.provide` with its window part's context: Settings → Accounts and hosts, `git.accounts`, which the Git module declares, shows each host's cards, its mark in the host's own colour and each card's title and detail, with Sign in on a signed-out or failed card, which opens the host's sign-in component in a kit dialog under the host's context, and a chip and a manage button, which opens the same dialog, on a signed-in or waiting one. Add an account lists the hosts and opens the same dialog. Under the cards, What each host can do shows which `GitHostFeature`s each host lists. The window part gives Settings search one row per host, `git.account.<id>`, which the page marks on the host's cards, and follows the hosts while it is active, since only the module that declares a page may give its rows.
A commit's author shows as a picture once one is known, or as their initials until then: host modules add pictures through `GitAvatars.provide`, asked in the order they were given by folder, email and commit, and the window part adds Gravatar's as the fallback, asked only once every host has none, so a picture doesn't change once shown. The Gravatar fallback reads each email once through `git.avatar` while the window part is active.
The workspace page, the `git.workspace` document, lists a workspace's repositories, or with the instance `open` the repositories opened lately, titled Dashboard, each with its branch, how far it is from its upstream and its changes; `git.openWorkspace`, titled Open dashboard, opens it with `{ id }`, or the Dashboard with `{ id: null }` or no arguments.
Add repository on that page asks `git.scanRepositories` about the chosen folder: a folder in a repository is added as it is, a folder with repositories in its subfolders opens a dialog listing them all ticked, relative to the folder, and adds the ones still ticked when the person clicks Open, and a folder with none says so in the page's result line.
Each listed repository has one row, made once and kept while it is listed, whose reads the table and the Across repositories view share. The page reads every listed repository once when it opens, four at a time, skipping one a row on screen already reads, and again when the window regains focus; only the rows on screen watch their repositories in between. Fetch all fetches four at a time, each on the fingerprint of a status read just before it, and a failure stays on its own row.
The row's Pull request and Checks cells are the current branch's own pull request; its Open cell counts the repository's open pull requests and those failing their checks, from the claiming host's whole open list through `GitWorkspacePullRequests.openListOf`, read once for each remote, a host that reads branches too, and again when the window regains focus. The cell is empty until the host answers the list, and it is the first column to leave as the page narrows.
The Repository panel's pull request rows have a context menu: Switch to branch, which switches to the pull request's source branch as the branch rows' switch does, git making it from the remote's branch when it isn't here, and is off on the current branch's own; Open in browser; and Copy link.
A history document brings the Repository view, `git.repository`, forward through `showView` each time it becomes the window's active document, in whatever dock the person put it, which also moves the focus there, as `showView` always does.
The Workspaces view, `git.workspaces` in the left dock's first group at order 20 after the Repository view, is the pages' menu: the Dashboard, then the workspaces with New workspace, each opening its page or bringing it to the front, then the Views and Hosts of the workspace page in front, which it follows through `GitWorkspaceSides` as a `GitWorkspaceSide`, kept while a document of another kind is in front, never opening the view. One item is chosen at a time: a view while the page shows one, else its workspace or the Dashboard, and choosing the chosen page's item shows all its repositories again.
The Views count the repositories read so far that are behind their upstream, have uncommitted changes or conflicts, have an open pull request waiting for review, or have an agent working or waiting for the person through `GitAgents`; choosing one shows only its repositories and reads every listed one once, and choosing it again keeps it. The Hosts list each host that claims a repository's remote through `GitPullRequests`, signed out when a row's read says nobody is signed in, else signed in once one answered, else with its count of remotes, and a click opens the host's page in Settings; the remotes no host claims follow as Plain Git, one row for each way Git reaches them.

## The local runtime part

The runtime part runs the person's own `git` through Noldova Desktop's `startProcessAsync`, never a shell, with the C locale, no prompt and no pager, and a path is never read as a pattern: a read sets `GIT_LITERAL_PATHSPECS=1`, and a write, whose hooks would inherit that setting and read their own globs literally, marks each path it names with the `:(literal)` pathspec magic instead; it runs with the person's `HOME`, or on Windows `HOMEDRIVE` and `HOMEPATH`, so git finds their own configuration; every run adds `-c core.fsmonitor=false`, so a command that a repository's own configuration names as its fsmonitor never runs from the module's reads, polls or writes, every read adds `--no-optional-locks`, so it never takes a lock another git client needs, and every path comes after `--`.
Before each status and diff, the runtime reads which filter drivers the repository's own configuration, `local` or `worktree` scope or a file it includes, gives a `clean` or `process` command, and switches each off for that read with `-c filter.<driver>.clean=`, `-c filter.<driver>.process=` and `-c filter.<driver>.required=false`, so a status or diff never runs a command that came with the repository.
It reads the same of each checked-out submodule's own configuration, at any depth, since git's status runs inside each submodule with that submodule's configuration, and git passes the options on to it; a repository with more than 256 checked-out submodules isn't read, as `Unavailable`. A driver whose name holds `=` can't be named in an option, so the read fails as `Unavailable`.
The person's own system and global filters still run, as for their own `git status`: Git LFS, which `git lfs install` sets up in the global configuration, works as before; an LFS set up only in the repository's configuration is switched off, so a tracked LFS file that git hashes again shows as changed, against its pointer.
A write runs the repository's filters as the person's own git does, a known limit: a person's click is their own `git add` or `git switch`, and switching a filter off would store or check out something else, such as an LFS file's whole content instead of its pointer. An agent's stage or switch names, in its request, each driver the repository's own configuration gives a command that write runs: `clean` or `process` for a stage, which then asks at low risk, and `smudge` or `process` for a switch. When `submodule.recurse` is set, a switch checks out each checked-out submodule too, so its request also names each of those submodules' hooks, with the submodule's path, and the `smudge` or `process` drivers its own configuration names, at any depth, found by the same submodule walk as the reads.
The diffs pass `--no-textconv` and `--no-ext-diff`, so a textconv or external diff command never runs.
Each run has an output limit and a time limit, and a run past its time limit is stopped.
A run cancelled or past its time limit fails as soon as its program has exited, without waiting for the rest of its output: a process the program started that outlived it, such as one that left its process tree, may still hold the output open, and the run never waits on it.
A read first checks, once while it passes, that `git version` is 2.39 or later, the oldest whose output the module reads; an older git's failure names its version, such as `2.34.1`, in `gitVersion`.

Each method takes a folder, finds the repository's top, git folder and common git folder with `git rev-parse`, and reads one read at a time per repository and kind: `git.status` shares its queue with the tools' reads and the repositories service, and each other read method has its own, so a slow status never holds the graph or the branches; callers asking for the same read while it still waits in its queue share its answer, which is cancelled only when all of them cancel.
`git.diff` answers the diff of the worktree, the staged changes or a range of two revisions, which come after `--end-of-options`, with each file's hunks and lines up to 1 MiB a file and 4 MiB in all, and the worktree's untracked files after its tracked ones, at most 1,000; a staged or range diff those limits cut also carries the whole diff's totals from `git diff --numstat`, so its header counts every file.
`git.diffTotals` answers those totals alone for any scope, the worktree's without its untracked files, so a card or a tab's count can show a large range's files and lines without reading its diff.
A renamed or copied file carries Git's similarity score from its raw entry, such as 92 from `R092`, and the commit's file list shows it after the change letter, as `R 92%`.
`git.branches` answers the local branches in git's order, the branch HEAD names, also before its first commit and `null` on a detached HEAD, the remotes' names, and the remotes' branches as `<remote>/<branch>` without each remote's `HEAD`.
Its `tips` give each local branch's commit id and its committer date with its offset, read with the branches in the same `git for-each-ref` call, so a caller can create a branch at another branch's tip without switching to it, or tell an old branch from a new one.
`git.mergedBranches` answers which local branches are merged into the branch the first remote's `HEAD` names, in `git remote`'s order, and that branch, such as `origin/main`.
It reads the remotes and `refs/remotes` as `git.branches` does, takes the first remote whose name is a branch name and that has a `HEAD`, builds `refs/remotes/<remote>/HEAD` from it and passes it as one argument to `git symbolic-ref --quiet --short` and to `git for-each-ref --merged=<ref> refs/heads`; a `HEAD` that names no branch is its own base, such as `origin/HEAD`, and without one the answer has no base and no branches.
It runs two more git commands than `git.branches`, so it is a read of its own that a view asks for only when it shows it, and the reads every change refreshes stay as they were.

`git.remoteTracks` answers how far each remote branch, as `<remote>/<branch>` without each remote's `HEAD`, is ahead of and behind HEAD, keeping only those that aren't level with it, in git's order, as `GitRemoteTracks`.
It needs `%(ahead-behind:HEAD)`, which git has from 2.41: on an older git, checked with the version the repository read already took, and when `git rev-parse --verify --quiet HEAD` exits 1, before HEAD's first commit, it answers none and runs nothing more; otherwise it runs one `git for-each-ref --format=%(refname)%09%(ahead-behind:HEAD)%00 refs/remotes`, which counts every branch in one walk, and refuses a record it can't read.
The Repository panel asks for it only while its Remotes section is open, again after each read of the branches, and draws each remote branch's counts on its row as the local branches' are drawn; a failure leaves the rows without counts.

`git.commitSigning` answers whether git signs a new commit in the repository and in which format, as `GitCommitSigning`, from `git config --type=bool --get commit.gpgsign` and `git config --get gpg.format`, which read every scope git reads and run no program; an unset setting, exit 1, is unsigned and OpenPGP, git's defaults, a `gpg.format` git doesn't know is a `null` format, and any other exit, such as 128 for a `commit.gpgsign` that isn't a boolean, or cut output fails as `Unavailable` with git's errors.
The Git view reads it again with each status read and when the window takes the focus, since a configuration change has no change event, keeping the last answer for the folder while a read runs and showing only the newest read's answer; the commit card ends its amend row with a muted note, "Signed with SSH key", "Signed with a GPG key" or "Signed with an X.509 certificate", only when git signs in a format it knows; a failed read shows no note and is logged.
`git.log` answers HEAD's newest commits, up to the request's limit and none before the first commit, each with its id, parents, author's name, authored time with its offset and subject, never the author's email; a name or subject has each control character replaced and is cut to 1,000 characters, and `truncated` says HEAD has more.
`git.messageReferences` answers which of the newest commits, up to the request's limit and in the order `git.graph` reads them, every branch, remote branch and tag with HEAD by date, name Azure Boards' `AB#N` anywhere in their messages: `git log --format=%H` lists their ids, then `git log --no-walk=unsorted --stdin --extended-regexp --grep=AB#[1-9][0-9]{0,9}` keeps the ones whose messages match that fixed pattern, never one built from the repository or the request, and each message is matched again so `AB#N` inside a longer word, path or link doesn't count. The answer holds only each commit's id and its numbers, each once in the order the message first names them, and `truncated`; an empty repository or an unborn HEAD answers none, and a failed run fails as `Unavailable` with git's errors, never a message's text.
`git.worktrees` answers the repository's worktrees from `git worktree list --porcelain -z`, the main one first, each with its folder as git prints it, the commit and branch it has checked out, `null` before the first commit, on a detached HEAD or for a bare repository, and whether it's locked or prunable; a list past 4 MiB fails as `Unavailable`.
`git.pullHooks` answers which of the hooks a pull runs, `post-merge`, `post-index-change` and `reference-transaction` in that order, git would run from the folder it takes hooks from, `core.hooksPath` too, as the commit request names its hooks; it fails as `Unavailable` when git can't name that folder or a hook's file can't be read, and the Git view's tooltip then keeps saying a pull runs the repository's hooks.
`git.scanRepositories` takes a folder the person chose and answers `GitRepositoryScan`: when the folder is in a repository, that it is, and otherwise the repositories in its subfolders, sorted, each a folder holding a `.git` folder or file. It reads folder names only, four folders down at most, a repository's own subfolders too, so a repository nested in another is found; it skips `.git`, `node_modules`, `_build`, `bin`, `obj`, `dist`, `target`, `vendor`, `.venv`, `venv`, `__pycache__` and `.cache`, follows no link, passes over a folder it may not read and stops at 1000 repositories.
`git.conflict` answers one unmerged file for the conflict screen: its kind, the operation in progress, the text of its base, ours and theirs stages from `git ls-files --stage --unmerged` and `git cat-file blob`, `null` for a missing stage, and git's merge of them with zdiff3 markers, which `git merge-file -p --zdiff3` makes over copies in a private temporary folder, so the read never touches the worktree or the index. A stage that isn't a regular file, is past 4 MiB, holds a NUL byte in its first 8,000 bytes or isn't UTF-8 makes the file binary, with no texts, so only whole-side choices are offered. While the file is unmerged but its worktree text has no marker lines, as git's recorded resolutions leave it, the merge is that text and `reused` says the person checks it. The sides' names come from the operation: the current branch, or `HEAD` when detached, against the merged branch or commit, `commit <id>` for a cherry-pick and `revert of <id>` for a revert; a rebase replays your commits onto another branch, so its ours is `onto <branch>` and its theirs `your commit <id>`. A file no longer unmerged fails as `Stale`.

`git.markerCheck` answers the tracked files, staged or not, that still have a conflict marker line, each once, as `git diff --check HEAD` finds them, the check `git.continueOperation` runs before it continues; the conflict screen lists those out of conflict under Before you commit.
The conflict screen's Resolved group holds the files the operation conflicted on that are out of conflict now: it asks `git.predict` once per merge, cherry-pick or revert for the paths merging its head commit into HEAD conflicts on, so a file resolved before the screen opened, outside it or before a restart counts too, with the choice that resolved it only when the screen did: ours, theirs, deleted, both when the merge editor kept both sides of every conflict, and edited for any other text; the write for both and edited is the same text. A rebase's operation names its branch, not the commit it applies, so its Resolved group holds only the files resolved on the screen while it is open.

`git.predict` answers what merging a commit into HEAD, or cherry-picking or reverting it there, would do, without touching the worktree or the index: `UpToDate`, `FastForward`, `Clean`, or `Conflicts` with the paths that would conflict, from `git merge-base --is-ancestor` and `git merge-tree --write-tree --name-only -z`. A cherry-pick is taken against the commit's first parent and a revert against the commit, with `--merge-base`, which needs git 2.40, so on an older git, for a root commit, and while the repository's own configuration names a merge driver, the answer is `Unavailable`; a pick whose result is HEAD's tree is `UpToDate`. The repository's own filters are switched off for `merge-tree`, as for a status. `merge-tree` writes the merged objects to the object store, never a ref, and a conflict git's recorded resolutions would resolve is still predicted as one.

`git.rebasePlan` answers what rebasing the current branch onto a commit would replay, as `git rebase -i` lists it: the merge base, how many commits the target is ahead of it, and the commits from the base to HEAD, oldest first, without merges, read with `git log --reverse --topo-order --no-merges`. A `fixup!`, `squash!` or `amend!` commit, the prefixes repeated or not, is paired with the nearest earlier commit whose subject is the rest of its subject, or whose id starts with it when that is 4 or more hex characters, as `--autosquash` pairs them. It names the other local branches on the replayed commits, and says whether the branch's upstream already has the oldest of them. A branch with more than 500 commits past the base is refused as `TooLarge` before they are read. It changes nothing.

`git.rebaseCheck` checks an interactive rebase's steps before it starts. Each kept step's commit is replayed with `git merge-tree --merge-base=<commit>^1`, starting from the target and then onto the tree the steps before it left, conflict markers and all, so a step moved above the commit it builds on shows its conflict. A step answers `Clean`, `Folded` for a squash or fixup, `Conflicts` with the paths, or `Dropped`. It needs git 2.45, whose `merge-tree` merges trees, so on an older git, and while the repository's own configuration names a merge driver, every step is `Unavailable`. As for `git.predict`, the repository's filters are switched off and `merge-tree` writes objects but never a ref.
`git.watch` and `git.unwatch` count each window's watches of each folder; while any window watches a folder of a repository, the runtime watches the repository's HEAD, index, branches and packed refs, polls every 5 seconds, and answers `git.watch` once the watch has started: after writing an empty `noldova-watch-<random>` file into the git folder and a `noldova-watch-<random>.lock` into `refs/heads`, it waits until each folder's watcher reports that file, then removes it; a file not reported within 5 seconds counts the watch as started anyway and is logged with its folder, and after a 200 ms debounce reads the status, and when its fingerprint moved it sends `git.changed` with the watched folder to each window watching one of the repository's folders, the first read included. While the module's own write runs, the runtime starts no such read, since the files change midway; when the write ends it sends `git.changed` at once, with no read first. The first `git.status` read after a write that starts and ends with no write starting or ending gives the fingerprint the next refresh compares against, so the watcher's echo of a write the windows have already read stays quiet, while a repository that moves on after that read, as one can while a checkout settles, is still announced. A closed window or connection drops its watches, and an unwatch or a closure that comes while a watch's repository is still being read cancels that watch. A watch whose start fails answers the failure and forgets every window's watches of the repository and stops its monitor, so Check again starts it afresh; a watch asked once the part has deactivated starts nothing.
`git.status` reads:

- the branch, HEAD, upstream and entries from `git status --porcelain=v2 -z`, at most 10,000 entries, with every option the person's configuration could change fixed;
- each changed side's line counts from `git diff --numstat -z`, the index against HEAD with renames and the worktree against the index without, a binary file's as none; an untracked text file counts its own lines, up to 1 MiB a file and 32 MiB in all, and a binary file, a path that isn't UTF-8 or a file past the limits counts none;
- the upstream's commit, as of the last fetch, from `git rev-parse --verify --quiet @{upstream}^{commit}`, none when the branch has no upstream or it is gone;
- the merge, rebase, cherry-pick or revert in progress from the files git keeps in the worktree's git folder, where a rebase wins over the commit it picks and a mailbox apply shows none;
- the remote from `git config`: the one the branch's configuration names, else the repository's only remote, with its host and path read from an HTTPS or SSH URL or an scp-style address, never the URL itself or the name, password, token or port in it; a local path or `file://` remote names no host or path, and a path with an empty, `.` or `..` segment names none;
- the fingerprint, a SHA-256 of the status's output, the index file's size and times, and each listed path's size, times and mode, so it moves when HEAD, the index or a changed file does.

A failure answers with Noldova Desktop's code and a `GitFailure` in the details: `Stale` as `Conflict`, `NotRepository` as `NotFound`, `Unavailable`, also a missing or older git and a folder the person's account may not read, as `Unavailable`, `Refused`, also a request the protocol refuses, as `InvalidParams`, and every other as `Internal`.
No message holds a URL's name, password or token, also when git prints one.

The runtime part also publishes `git.repositories`, a `GitRepositories` from the Git protocol, for the modules that declare `git` among their dependencies, such as a host module's agent tools.

The Git module declares the checkpoints module as an optional dependency, at one exact version, and its runtime package depends on `@noldova/checkpoints.protocol` alone, never on that module's code. For each discard and its undo it looks up the checkpoints module's `checkpoints.service` with `findService` and a guard of its own, so it works the same without the module, only with discards that can't be undone; `git.journal` says which applies.
It only reads: `readStatusAsync` reads a folder's status as `git.status` does, with the same folder check, the same queue per repository and fsmonitor off, and rejects with the same failures; `readRemoteAsync` reads one remote by its name, such as `origin`, whatever remote the branch works with, the same way.

### Worktrees

`WorktreeService` makes and removes a worktree for an app's opaque key, which never appears in a path or a branch name. The runtime part declares its `worktrees` table's migration, `create-worktrees`, and runs `reconcileAsync` at activation, which with no records runs nothing. Since the part declares a migration, Noldova Desktop opens and migrates the module's database before activation, and a database that can't open or migrate fails the whole Git module, its reads, writes and tools too. The reconcile runs before the module's methods register, so once records exist, each record's and each recorded repository's git runs delay them. No method, tool or published service reaches the rest yet, and each removal brings its caller's permission gate.

- `createWorktreeAsync(key, options)` runs `git worktree add --lock --reason <reason> -b <branch> <path> <base>`, with the path under the module's work folder, outside the repository, the base HEAD and the branch `noldova/<id>` unless the options name them, so the worktree is locked in the same step; the module knows its own lock by the reason. The same key always gives the same record, and a key whose worktree is in another repository is refused. `git worktree add` runs the repository's `post-checkout` hook, as checking out a branch does.
- A record is written to the module's `worktrees` table as pending before `git worktree add` runs, and marked ready once it succeeds, so an interrupted create leaves a pending record the module clears later.
- `removeWorktreeAsync(key, options)` asks the options' permission gate first, with `git.removeWorktree`, when the worktree has changes: the tracked and untracked paths `git status` reports, bound by a digest of the status and each changed file's content, so a change after the answer keeps the worktree as `Stale`. Ignored files don't count, and go with the worktree. It then unlocks and removes it; the branch stays unless the call asks to delete it, and `git branch -d` keeping it fails as `BranchUnmerged`. A worktree another tool locked is never touched, as `LockedElsewhere`.
- The module never runs `git worktree prune`, which can't target one entry. It clears its own stale entry, a pending one or one whose folder is gone, by unlocking it and running `git worktree remove --force <path>` on that entry alone, then drops the record; the next create for the key makes a fresh worktree on a new path and branch.
- `reconcileAsync()` clears each stale record as above, then reads each recorded repository's `git worktree list --porcelain -z` and logs, without touching it, each worktree it didn't make.
- `statusAsync(key)` and `diffAsync(key, scope, paths)` read the key's worktree as `git.status` and `git.diff` do.

### Writes

Each write method takes a folder and `basedOn`, the fingerprint of the status the person saw, and answers `null`; the window reads the status again on the `git.changed` that follows.
They are the person's own clicks: each answers `Unauthorized` to any caller but the app's main process acting for a window, before it reads its parameters, and never asks; an agent writes only through its tools, which raise Noldova Desktop's permission requests, as [SECURITY-MODEL.md](SECURITY-MODEL.md) says.
`WriteRunner` runs each write: it reads the status and refuses one whose fingerprint moved as `Stale`, lets the write refuse what the status can't take, asks an agent's call the write's request, and then, one write at a time per repository, reads the status and the request again and runs the write only when both are unchanged; an agent's request is read again even when it asked nothing, so a hook or filter added while the write waited is `Stale` rather than run without an ask.
A write cancelled or past its time limit after git started fails as `OutcomeUnknown`, and the repository's watch refreshes after every write that ran.
Each git command a write runs goes into the repository's command log, which `git.commandLog` answers: the last 200 while the module runs, each with when it started, its command line as the person could type it, without the module's `-c` settings or `--end-of-options` and with a URL's name and password taken out, its exit code, `null` when it didn't run to its end, and how long it ran; the index snapshot an undo takes is the module's own and isn't logged.
The window shows it in the command log view, a tab per repository that opens in the bottom dock and stays wherever the person moves it; the tab watches its own repository, whichever one the Git view shows, and reads the log again on each `git.changed` for it, and the window part keeps the open logs' folders in the window's storage and reopens them where they were when it activates.

### Platform and git details

- Each git run gets `HOME`, or on Windows `HOMEDRIVE` and `HOMEPATH`, so git finds the person's own configuration, such as their identity, as their terminal's git does; Noldova Desktop passes only `USERPROFILE` on Windows, which not every Git for Windows reads as the home when `HOME` isn't set.
- A write that names paths splits them into runs that each fit one command line, since Windows takes at most 32,767 characters in one, with room for git's own arguments and each path's quotes.
- A hook counts as one git would run when it is a regular file that is executable, or, on Windows, where files carry no executable bit, one that starts as a script (`#!`) or a program (`MZ`), as Git for Windows tells them; the rule reads the starts each platform accepts, none outside Windows, with no branch on the platform, and each target's tests check its own platform's rule.
- The changes digest binds the whole status, which holds the index's object ids and modes, and the content of each changed path; it reads at most 1 GiB of changed content within 60 s, so a huge or slow file fails the request clearly instead of holding it.
- The change monitor watches the worktree's `HEAD` and index, the branches directly under `refs/heads` and `packed-refs`, each folder without recursion; for a repository whose `extensions.refStorage` is `reftable`, which `git.watch` reads with `git config --get extensions.refStorage`, it watches `reftable/tables.list` in place of `refs/heads`, which git rewrites as each ref change ends, and writes no cookie there; file edits and branches in nested folders, such as `feature/x`, are found by the poll while the pane is visible, and when it becomes visible.
  On Windows and macOS, whose file watch covers a folder tree natively, it also watches the worktree's whole tree; on Linux, whose watch covers one folder, it watches each folder git doesn't ignore while the worktree shows, walking the tree a level at a time with one `git check-ignore` a level, adding a folder made later, dropping one removed, and walking again when a `.gitignore` changes. A shown worktree whose files are watched is polled every 60 seconds in place of every 5, to catch a change the file system didn't report. A worktree with more than 10,000 folders git doesn't ignore, or whose watch fails, as one does once the system runs out of watches, keeps the 5-second poll, and the log says why; elsewhere the 5-second poll stays.
  It collects a shown worktree's changed paths until its files go quiet for 300 ms, or 2 s into a stream of changes, and refreshes only when `git check-ignore` finds one git doesn't ignore, or can't tell, which it logs; paths in the git folder are left to the git folder's own watches, a changed `.gitignore` counts as a change, and a hidden worktree's changes are left to the read that showing it starts.
  The check remembers which folders git ignores until an ignore file changes, so a build writing into `bin` or `node_modules` costs one check, not a status read for each file; a path whose folder form git ignores, such as `bin` for `bin/`, counts as ignored, since a watch can name the folder a file changed in, and a tracked file inside an ignored folder is left to the 60-second poll.
  When git's folders can't be watched, the monitor logs why and polls the worktree every 5 seconds for as long as it is watched, visible or not.
  A cookie the monitor can't write, because the folder is read-only, gone or denied, is logged and the watch counts as started at the 5-second mark; on start the monitor removes only `noldova-watch-*` files an earlier run left in the git folder and `noldova-watch-*.lock` in `refs/heads`, never another live watch's cookie.
- A conflict that git combines has a raw entry starting with `::` in `git diff -z --raw --patch`, and its `diff --cc` patch is left out of the diff.

## Signing in to GitHub

The GitHub module's runtime part signs in with GitHub's device flow, as Noldova's GitHub app, whose client id is public and which has no client secret.
Its requests, the sign-in's to `github.com` and the token's to `api.github.com`, follow no redirect: a redirect is refused like any other status that isn't a success, so no body, device code or token is sent on to another host.
It reads an answer a chunk at a time, at most 64 KiB for the sign-in's and 8 MiB for the API's, and refuses a longer one, letting go of the rest, rather than holding whatever GitHub sends.
It asks for the `repo` scope, and the sign-in's state is a `HostSignIn`: signed out, with the failure that ended the last sign-in if one did; waiting, with the code the person enters at GitHub's address; or signed in, with the account's login, name, avatar and the scopes GitHub granted.
The account's avatar reaches a window only as a base64 data address, or null, never as GitHub's address for it: once GitHub answers the token's account, the part keeps and shows the account at once, then reads its avatar the same way and with the same reader as a reference author's avatar, below, and shows the account again with it, unless the sign-in changed meanwhile.

| Member | What it does |
|---|---|
| `git-github.readSignIn` | Answers the sign-in as it is. |
| `git-github.startSignIn` | Asks GitHub for a code and answers the waiting sign-in; while one waits or is signed in, it answers that one. |
| `git-github.cancelSignIn` | Stops a waiting sign-in, which ends signed out with no failure. |
| `git-github.signOut` | Stops a waiting sign-in, or forgets the kept token, and answers the signed-out state. |
| `git-github.signInChanged` | The event that carries each new state. |

While a sign-in waits, the runtime part polls GitHub at the interval GitHub names, at least a second and five seconds when GitHub names none, waiting longer whenever GitHub asks it to slow down: at the interval GitHub then names, or five seconds more.
It refuses a code whose expiry isn't between a second and an hour.
A sign-in ends signed out with `Expired` when the code expires, `Denied` when the person refuses it, `Unreachable` when GitHub can't be reached or doesn't answer in 30 seconds, `Refused` when GitHub answers something the part can't use, and `Unkept` when the token can't be kept; a sign-out whose token can't be removed from the secrets ends signed out with `Unforgotten`, since a later start may restore it.
Only the secrets' own failures, a `MethodFailureException`, count as `Unkept`, `Unforgotten` or an unreadable kept sign-in; any other failure is passed on as it is, to the caller or the log's unexpected-failure line.

The token never leaves the main process: the window parts see only the account.
One other module can read it: the runtime part publishes `git-github.access`, an `IGitHubAccess`, exported from `@noldova/git.github/runtime` and `@noldova/git.github.protocol`, whose `accessAsync(signal)` answers the held token with the account's login, as a `GitHubAccessGrant`, or why there is none, as a `GitHubAccessRefusal`: "Sign in to GitHub in Settings, GitHub." signed out, a sentence on the kept sign-in that Noldova Desktop couldn't read, or one on entering the code while a sign-in waits; an aborted signal rejects with its reason.
Only a module that names `git-github` as a dependency or an optional dependency can find it, as Noldova Desktop's services go.
Any such module of the app gets the token, with every scope it holds, and the part doesn't ask who reads it: every module of an app is Noldova's and has the app's privileges, as Noldova Desktop's [Trust](https://github.com/noldova-com/desktop/blob/main/documents/MODULES.md#trust) says, so a check inside the one process would only be advisory, since a module could read the token around it.
This is decided for modules Noldova writes: if an app ever loads a module from outside Noldova, the service first takes a list of the modules that may read it, which Noldova Desktop enforces, and refuses any other with the reason.
An app's module that names `git-github` as an optional dependency can read it each time it passes GitHub's own MCP server to a turn, so signing out stops the next turn's token; nothing logs it.
It is kept with its account, without the avatar, in Noldova Desktop's module secrets as `git-github.signIn`, encrypted for this computer only; a sign-in kept by an earlier version, with the avatar's address, still restores, with no avatar.
On activation the part shows the kept account at once, with no avatar, and then asks GitHub for the token's account and its avatar: an answer replaces it, a token GitHub no longer accepts is forgotten and ends signed out with `Revoked`, and a token GitHub can't check now stays.
While the app's main process isn't connected yet, the part reads the kept sign-in again once the app's windows change.
Signing out forgets the token on this computer only; the person withdraws Noldova's access on GitHub's page for the app, which `GitHubNames.manageAccessUrl` names.
Changing which scopes it asks for, where the token is kept or what reaches the windows is a risky change, as the repository's `AGENTS.md` says.

On activation the window part gives Accounts and hosts its account through `GitHostAccounts.provide`, with `GitHubSignInComponent`, `nol-git-github-sign-in`, as its dialog: the Account section that signs in, shows the code, the account and a failure, and signs out.
Its card says GitHub and what signing in brings while signed out, the code's note while a sign-in waits, and the account's login and access once signed in; a read that fails says the sign-in couldn't be read.
It reads the sign-in when it opens and follows `git-github.signInChanged` until it closes.
Signed out, it says what signing in brings, or why the last sign-in ended, and offers the sign-in.
While a sign-in waits, it shows the code, copies it and opens GitHub's page for it, offers to copy the code and to copy it and open the page again, and counts down to the code's expiry each second.
GitHub's page for the code, and its page for the app's access, open in the person's own browser whatever the Links setting says, with `LinkPlace.System`, since both need the person's GitHub session, which the app's Browser doesn't have; the code is on the clipboard to paste there, and the note says so only when the clipboard took it.
Signed in, it shows the account's login beside its avatar, or its initial when it has none, and whether it reaches the person's repositories, and offers to sign out or to open GitHub's page for the app's access.
It holds its sign-in, cancel and sign-out buttons while a request is out.
A request that fails logs why and shows a banner, "GitHub's sign-in didn't answer.", which says to try again; when the first read fails, the page shows only that banner under its title, with Try again, which reads the sign-in again.
A page it can't open, GitHub's page for the code or for the app's access, logs why and shows the banner "The page couldn't be opened." instead.
The banner clears at the next request and when the sign-in's state changes; a sign-in event in the same state, such as a late Waiting or an avatar arriving, leaves it, so a late event can't wipe a fresh notice.
On activation it shows the signed-out card, then reads the sign-in and follows `git-github.signInChanged` until it deactivates, showing the card of what the dialog shows.
A sign-in read that answers after a change event arrived is dropped, since its answer is older than the event's.
A read that answers after the part deactivated shows nothing.

On activation the window part gives the Git view its host row through `GitHostRows.provide`, for remotes on github.com, and withdraws it on deactivation.
It also gives the repository panel the remote's open pull requests through `GitPullRequests.provide`, `GitHubPullRequests`, for the same remotes, as the Azure DevOps module does: it reads them through `git-github.readPullRequests` on each refresh, keeps the rows it showed while it reads, drops an answer a newer read overtook, says when nobody is signed in, whose sign-in the `git.accounts` page holds, and shows the runtime's message for a failed read, or that GitHub didn't answer.
For the workspace page's Needs you it has `reviewsFor` and `refreshReviews`: one list for each remote, read through `git-github.readReviewRequests`, whose rows carry the reference, label, title, page and draft flag but no counts or head branch, and which keeps the rows it showed after a failed read, such as GitHub's rate limit, logging it.
For the commit detail it has `commentsFor`, read through `git-github.readCommitComments` once for each remote and commit, the answer kept in the window and a failed read logged and dropped so the next showing reads again.
For the history's branch drop it has `newPullRequestUrl`, the repository's compare page between the two branches, with `expand=1` so GitHub opens the new pull request's form.
Each row is labelled `#N` and keyed by its reference's text, and a click opens its page in the browser.
It also gives the Git view its link source through `GitLinkReferences.provide`, made the first time the view asks: `GitHubReferenceSource` knows github.com issue and pull request addresses and `owner/repo#N` in text, and a bare `#N` in a repository whose remote is on github.com. Signed in, it reads each item once through `git-github.readReference`, at most four at a time, and keeps the last 500. Signed out, or when a read fails, the link stays plain.
It also gives the Git view its authors' pictures through `GitAvatars.provide`, made the first time the view asks: `GitHubAuthorAvatars` waits for the folder's remote, has none for a remote off github.com, and reads each repository's author once through `git-github.readAuthorAvatar`, again after each change of the sign-in.
The row, `GitHubHostRowComponent`, reads the sign-in and follows `git-github.signInChanged`; signed in, it reads `git-github.readBranchPullRequest` for the remote's host and path, the branch and HEAD, and reads again whenever one of them changes, dropping an answer or failure for a branch it has left.
It shows the pull request's state icon in GitHub's look, its number and title, which open it on GitHub as its open button does, and its checks worst first, failed then running, queued, passed and skipped, each with its state's Octicon and label; a check's name opens its run.
A title or name the row cuts off is marked `data-truncates`, as the kit does, and shows in full in the kit's tooltip only while it is cut.
A branch with no pull request, or a detached HEAD, shows "No pull request for this branch".
Signed out, it offers the sign-in, then shows the code with Copy code and Cancel, copies it and opens GitHub's page for it in the person's own browser, as the sign-in page does; while GitHub doesn't answer, it says so and offers Try again.
A pull request and a check's run open where the Links setting says, like every link.
A page the row can't open, GitHub's page for the code during a sign-in, a pull request or a check's run, logs why and shows the notice "The page couldn't be opened" under the row, with Open the page again, which opens that page again in the same place, so beside the device code the person still reaches GitHub's page when the first opening failed.
The notice clears at the next opening and when the sign-in's state changes; as on the sign-in page, an event in the same state leaves it.
The GitHub window takes `@noldova/git.window` from the root's install, where the build installs the Git window's packed archive before it compiles the GitHub window, so its compile and its tests use the real `GitHostRows` as an app gets it.

## Reading GitHub

The GitHub module's runtime part reads issues, pull requests and checks, and opens pull requests, under the person's sign-in, with the hosting protocol's models.

| Member | What it does |
|---|---|
| `git-github.readReference` | Takes a `HostReference` and answers its issue or pull request as a `HostItem`, or null, with the author's avatar as a data address. |
| `git-github.readBranchPullRequest` | Takes a `BranchQuery`, with the remote's host and `owner/repository` path as the Git module reads them, and answers a `BranchPullRequest`: the branch's newest pull request in the repository, the check runs of the query's head commit, or of the pull request's head when the query names none, and its review decision: from each reviewer's latest review that approves or requests changes, `ChangesRequested` when one requests changes, else `Approved` when one approves, else `Waiting`; a dismissed review counts for neither. Only reviews by the repository's owner, members and collaborators count, by GitHub's `author_association`, which is close to write access but not exact: a member or collaborator may only read, and an organization's other members may count as `MEMBER`. |
| `git-github.createPullRequest` | Takes a `PullRequestDraft`, opens the pull request and answers it as a `HostItem`. |
| `git-github.readAuthorAvatar` | Takes an `AuthorQuery` and answers the author's GitHub picture as a `HostAvatar`: for a GitHub no-reply email, the account it names, without asking GitHub's API; signed in, the account GitHub links to the commit; else, and off github.com, none. |
| `git-github.readPullRequests` | Takes a `RepositoryQuery` with `github.com` and the `owner/repository` path, and answers a `HostPullRequestList`: the repository's open pull requests, the most recently updated first, at most 20 and whether there are more, each with its approvals, from the same latest reviews as the review decision, its head's check runs counted as passed, failing or pending, and its head branch; signed out, it answers the signed-out list. |
| `git-github.readReviewRequests` | Takes a `RepositoryQuery` like `readPullRequests`, and answers a `HostReviewRequestList`: the repository's open pull requests that ask the signed-in account for a review, its own or one of its teams', the newest first, each with its reference, title, page, draft flag and when it was opened. They come from one search of the account's review requests, `is:pr is:open review-requested:@me`, the 100 most recently updated, which `GitHubReads` holds for a minute whether it answered or failed and shares out by each item's `repository_url`, ignoring case: GitHub allows 30 searches a minute, so a workspace's repositories and every focus inside that minute share one. `hasMore` says the account's search was cut or incomplete, on every repository's list. A refused token is reported to the sign-in as for the other reads; signed out, it answers the signed-out list, and for a repository off github.com, none. |
| `git-github.readCommitComments` | Takes a `CommitQuery` for the same remotes and answers a `HostCommitComments`: it reads the commit's own comments and the first pull request GitHub links to the commit, then that pull request's review comments, one page of 100 each, and counts the commit's comments and the review comments made on it, by `commit_id` or `original_commit_id`, at most 100, capped when a page was full. The page to open is the first such comment's own address, kept only when it is an https page on github.com with no user name or password, and otherwise the answer is none. No comment answers none, as do signed out and a repository off github.com; a refused token is reported to the sign-in as for the other reads. |
| `git-github.readPullRequest` | Takes a `HostReference` to a pull request on GitHub and answers a `HostPullRequest` for its page, or none signed out, for another host or for one GitHub can't show: the item with its author's picture, its description (empty for none), its commit count, its reviewers, each person by their latest approval (1, "Approved") or request for changes (-1, "Changes requested"), as "Commented" (0) when they gave neither or it was dismissed, and the people and teams it still asks as "Review requested" (0), a team by its name, none required; the author, whose replies in a review's threads GitHub keeps as reviews, and a review not yet submitted (`PENDING`) are left out, as GitHub's own list leaves them, the check runs on its head as builds with their start and, once finished, finish times, whether auto-merge is on with its merge method, and `hasConflicts` from `mergeable_state`: `dirty` as true, `unknown`, which GitHub answers until it has worked it out, as null, and any other as false. It has no policies or work items, which GitHub doesn't keep; it reads every page of the reviews and check runs, and a refused token is reported to the sign-in as for the other reads. |
| `git-github.readPullRequestThreads` | Takes the same reference and answers a `HostPullRequestThreads`, its threads oldest first by their first comment: each conversation comment a thread of its own with no file, and each review comment with the replies to it a thread on its file and its line, or its original line once the line is gone; a reply whose first comment isn't on the page still groups with the others under that comment's id. GitHub numbers the two kinds apart, so a thread's id is its first comment's id doubled, plus one for a review comment's thread, and its comments keep GitHub's ids. A comment with no text is left out. GitHub's REST API keeps no resolved state, so every thread's state is `None`; a deleted account's comment shows as `ghost`. It keeps the newest 100 of each kind, with `hasMore` when there are older ones: GitHub lists comments oldest first, so it reads the pull request for its counts, starts at the page they put the newest 100 on and reads on, 100 at a time, while pages come back full, which also finds comments added after a count it read earlier. It answers no threads signed out, for another host or for a pull request GitHub can't show. |

Signed out, for a reference to another host module or a repository off github.com, or for what GitHub can't show the sign-in, a read answers null, or a `BranchPullRequest` with no pull request, without failing, so a link stays a plain link.
A read's answer is kept for 60 seconds; after that the part asks again with the answer's tag in `If-None-Match`, which GitHub doesn't count against the rate limit when nothing changed, and keeps the 500 answers read last, none longer than 262,144 characters, for the signed-in token only.
Signing out, or signing in as anyone, drops every kept answer, and an answer that lands after the token changed is neither kept nor answered.
A `HostItem` carries when it was opened, and when a merged pull request was merged or a closed one or an issue was closed, so an app can show either age.
Its author's avatar reaches a window only as a base64 data address, never as GitHub's address for it, since a window's content policy allows only its own and data images.
For `git-github.readReference`, and for the signed-in account, the part reads the avatar at 64 pixels from `avatars.githubusercontent.com` with no token or cookie, since avatars are public and the token goes to no host but `api.github.com`; it reads a reference author's alongside the pull request and the account's once the account is shown, gives the whole read, redirects included, five seconds, follows at most three redirects, each only on that host, cancels the body of a redirect or a refused answer, takes a PNG, JPEG, GIF or WebP image of at most 64 KiB, and keeps the 500 avatars read last.
An avatar it can't read, for an HTTP failure of any status, a network failure, the five-second deadline, an answer that isn't an image, an empty or oversized body, or too many or off-host redirects, leaves the author or the account without one and logs why, without failing the read; any other error is a defect of the module's own and fails the item's read.
An agent's `git_github_read` and the other reads carry no avatar.
The author's `url` is GitHub's `html_url` for them as GitHub gives it, an app's page for an app whether or not its login ends in `[bot]`, so a window links it as is rather than building it from the login; null when GitHub gives none or one that isn't an https address, which never fails the read.
The protocol refuses an owner, repository or path with a `.` or `..` name, `%2e` counting as a dot, or characters outside letters, digits, `.`, `_` and `-`; an owner or path may also hold percent escapes, such as `%20` in an Azure DevOps project's name, which the Azure DevOps module decodes before it encodes each name in its own addresses. The GitHub module also refuses an owner or repository outside GitHub's own names, so a reference never steers the token to another of GitHub's addresses.
A token GitHub refuses signs out with `Revoked` and fails the call as `Unauthorized`; GitHub out of reach or refusing fails it as `Unavailable`, a used-up rate limit naming the time it resets, and a timeout as `DeadlineExceeded`.

Only a person opens a pull request: `git-github.createPullRequest` refuses as `Unauthorized` any caller but the app's main process acting for a window, which is how a click in the module's window reaches it.
No agent reaches this method: Noldova Desktop raises a permission request only for a tool call, so an agent's way to a pull request is a tool that asks first.
GitHub refusing the pull request, for example because the branch already has one, fails it as `Conflict`.

The window part's `GitHubLooks` gives GitHub's look for each kind and state, so an app draws a GitHub reference chip and its card from a `HostItem`'s kind and state alone: the kind's and the state's labels in GitHub's words, the state's Octicon, and its colors and badge fill in light and dark, with GitHub's mark beside them.
Open is the ok status color, draft and not planned the muted text color, merged and a done issue GitHub's purple, #8250DF in light and #A371F7 in dark, and a closed pull request the failed status color.
The look is fixed in the module: no markup or color comes from GitHub's answers or the runtime part, and the icons are `data:` addresses an app draws as masks in the state's color, never markup it inserts.
The Octicons and their license are listed in the window part's `THIRD-PARTY-NOTICES.md`, with the check states' `check-circle-fill`, `x-circle-fill`, `dot-fill` and `clock`, which the host row draws the same way.

## Signing in to and reading Azure DevOps

The Azure DevOps module signs in to one organization from its account's dialog on Settings → Accounts and hosts: first with a personal access token the person makes in Azure DevOps and pastes, and below that, as a second option, with Microsoft, noting that the organization's admin may need to approve the app; the two swap once the app's publisher is verified.
The page fills the organization from the open repository's Azure DevOps remote, read through `git.status`, and the person types it when there is none; its "Make a token" link opens the organization's token page, on `{organization}.visualstudio.com` for a remote of that old form and on `dev.azure.com/{organization}` otherwise.
Under the token field it lists the scopes a token needs for what the module reads and writes: Code (Read & write) for pull requests, their votes and comments, Work Items (Read & write), Graph (Read) for people's pictures and Build (Read) for a pull request's checks.
A token is often scoped to one organization, which the profile on `app.vssps.visualstudio.com` refuses, so either sign-in asks the organization itself who signed in.
While a sign-in with Microsoft waits, the page says to finish it in the browser, with Open the sign-in again and Cancel.
Its card on Accounts and hosts says Azure DevOps and what signing in brings while signed out, to finish in the browser while a sign-in with Microsoft waits, and the account once signed in.

The sign-in with Microsoft is Microsoft Entra's authorization-code flow with PKCE, as a public client with no secret, through the person's own browser.
`AzureSignIn` makes a random state and code verifier, and `LoopbackRedirect` listens on `127.0.0.1` on a port the system picks, for one GET to `/` that carries the state and a code or an error; it answers anything else, a target that isn't an address too, with a 404, answers the first match with a plain page that says to close the tab, and closes.
The waiting `HostSignIn` carries the authorize address on `login.microsoftonline.com/organizations`, with the app's client id, the redirect `http://127.0.0.1:{port}`, the S256 challenge and the scopes `vso.code`, `vso.code_write`, `vso.work_write` and `vso.graph` on Azure DevOps' resource with `offline_access`; the window opens it with `LinkPlace.System`, since one access token holds one resource's scopes and the module reads nothing from Microsoft Graph.
`EntraFlow` redeems the code with the verifier, and the sign-in asks the organization's `connectionData` who signed in with the access token as a bearer token, then keeps the refresh token with the organization and the account as a token sign-in is kept, with its kind, but as `git-azure-devops.microsoftSignIn`, so an earlier version, which reads only `git-azure-devops.signIn`, never takes it for a token.
It renews the access token five minutes before it expires, on activation and when Azure DevOps refuses it, into the same credential, so a read in flight still compares as the one it was given, and keeps each new refresh token; when Microsoft refuses the renewal, the sign-in signs out with `Expired`, which asks the person to sign in again, except that a renewal refused only for the consent `vso.code_write` needs is asked again without it, keeping the sign-in for reads and work items, and the replies, thread states and votes then fail as `Unauthorized` with a sentence asking the person to sign in again.
A sign-in kept before the kind is a token sign-in.

| Method or event | What it does |
|---|---|
| `git-azure-devops.readSignIn` | Answers the sign-in as it is. |
| `git-azure-devops.startSignIn` | Takes `{ organization }`, opens the listener and answers the waiting state with the address to open; the sign-in then ends signed in, or signed out with `Denied` when the person refuses consent, `Refused` when Microsoft or the organization refuses it, `Expired` after five minutes, `Unreachable` when either can't be reached and `Unkept` when the secrets can't keep it. The sign-in is kept with its organization and account in Noldova Desktop's module secrets as `git-azure-devops.signIn`, or `git-azure-devops.microsoftSignIn` for a sign-in with Microsoft, encrypted for this computer only, and restored, the token's first, and checked again on activation as GitHub's is: a sign-in Azure DevOps refuses then signs out as `Revoked`; keeping either kind removes the other's, and sign-out tries to remove both, signing out as `Unforgotten` when either removal fails.
A sign-out during a sign-in forgets a token the sign-in saved after it.
The account's login is the authenticated user's `Account` property, an email address, and its name the provider's display name; Azure DevOps' avatars need the token, so the account has none.

Every request goes to `dev.azure.com` with a token as basic authorization, or Microsoft's access token as a bearer token, follows no redirect and times out after 30 seconds; a 401, a 203 or a redirect, which is how Azure DevOps answers a token it doesn't take, fails as `Unauthorized`; when it answers the held token, the sign-in asks `connectionData` again and signs out as `Revoked` only when that is refused too, so a token whose scope lacks one read or write stays signed in, a 404 answers nothing, a 429 fails as rate limited and any other refusal or an unreadable answer as `Unavailable`.

## Agent tools

The modules' runtime parts offer agent tools through Noldova Desktop's tool registry, which the app serves to its agents; they register each tool on activation and withdraw it on deactivation.

| Tool | Module | What it does |
|---|---|---|
| `git_status` | Git | Takes nothing and answers the bound repository's `GitStatus`. |
| `git_diff` | Git | Takes an optional `staged` and `paths`, each relative to the repository's top folder, and answers its unstaged, or staged, `GitDiff`. |
| `git_log` | Git | Takes an optional `limit`, 20 when left out and at most 500, and answers the current branch's newest commits as a `GitLog`. |
| `git_branches` | Git | Takes nothing and answers the repository's `GitBranches`, with `truncated` beside them. |
| `git_stage`, `git_unstage` | Git | Take `paths` and run `git.stage`'s or `git.unstage`'s write. |
| `git_create_branch`, `git_switch_branch` | Git | Take a branch `name` and run `git.createBranch`'s or `git.switchBranch`'s write. |
| `git_commit` | Git | Takes a `message` and runs `git.commit`'s write. |
| `git_push` | Git | Takes nothing and runs `git.push`'s write. |
| `git_pull` | Git | Takes nothing and runs `git.pull`'s write. |

| `git_github_pr_create` | GitHub | Takes a `title`, a `base` branch, an optional `body` and `draft`, and, once the person allows it, opens a pull request from the bound folder's branch into `base`, answering it as the `HostItem`'s JSON. |

- `git_github_read` is read-only and low risk, reaches GitHub, and has a 30 s deadline, at most 120 s.
- Its input schema allows only GitHub's own owner and repository names and a positive number, so the registry refuses any other argument as `Refused` without asking GitHub.
- Signed out, or once GitHub refuses the token, it fails as `Unavailable` with the module code `git-github.signedOut`, which tells the agent to ask the person to sign in; for what GitHub can't show the sign-in it fails as `Unavailable` with `git-github.notFound`, GitHub out of reach as `Unavailable` with `git-github.unavailable`, and a timeout as `TimedOut`; a cancelled call ends as Noldova Desktop's abort says.
- `git_github_pr_checks` is read-only and low risk, with the same deadlines; `git_github_pr_create` writes, is high risk, binds the `git.folder` resource, and has a 60 s deadline, at most 120 s, the registry's longest.
- Both read the bound folder's branch and its `origin` remote through `git.repositories`, never the remote the branch tracks, so a fork's pull request opens on the fork whatever the branch was made from: no usable `git.folder` fails as `Refused` with `git-github.noFolder`, a folder that isn't a repository as `Refused` with `git-github.notRepository`, no `origin`, or one that isn't a github.com repository, as `Refused` with `git-github.notGitHub`, a detached head as `Refused` with `git-github.detachedHead`, and Git or the Git module out of reach as `Unavailable` with `git-github.gitUnavailable`.
- `git_github_pr_create` asks the person first, every time, with a high-risk permission request whose action is `git-github.createPullRequest` and whose subject is the repository; its title names the repository and says when it is a draft, and its details show both branches and the draft flag as the module's text, and the title and the whole body as the agent's text. The body starts on its own line under its label, without trailing blank lines, and is left out when it holds nothing but white space; GitHub gets the body as given. The title's schema refuses a line break, so a title can't draw a false line on the card. It offers only to allow once and to deny, never to allow always, so no kept answer opens a pull request.
- A denial fails as `Denied`, an expired request as `Expired` and a withdrawn one as `Withdrawn`, all before anything reaches GitHub; a base branch equal to the bound branch is refused before asking. Once allowed, the call is sending: any failure from then on ends as `OutcomeUncertain`, keeping its module code, with `git_github_pr_checks` as the tool that finds out whether the pull request was opened.
- The Git module's tools act only in the repository that holds the bound folder, through the same readers, the same queue per repository and the same writers as the window's methods, and answer the repository's text as untrusted, with the origin `git:repository`: a read its `GitStatus`, `GitDiff`, `GitLog` or `GitBranches`, and a write the `GitStatus` after it, or, when that status can't be read, that the write is done and the agent should read it with `git_status`, so a write that ran is never answered as uncertain and repeated.
  A result past a tool result's size keeps as many items, entries, files, commits or branches, as fit and is marked `truncated`, and one that can't fit even so fails as `TooLarge` with `git.tooLarge`.
- The reads are read-only and low risk, with a 30 s deadline, at most 120 s.
- Each write bases itself on the status it reads first and runs through `WriteRunner` with the call as the agent's, so it asks at its writer's risk, as "Writes" says and [SECURITY-MODEL.md](SECURITY-MODEL.md) holds: stage, unstage and create a branch low, asking only when a hook would run or the hooks can't be read, switch and commit medium, pull medium and open-world, push high and open-world.
  Each takes its turn on the `git.folder` resource, marks its point of no return just before git starts, and has a 60 s deadline, at most 120 s.
- A Git tool fails with Noldova Desktop's code and the module code `git.<camelCase>` of the module's failure, with git's output as the repository's untrusted text: no usable `git.folder` as `Refused` with `git.noFolder`, though Noldova Desktop refuses a write with no `git.folder` at all before it runs, since the write takes its turn on that binding, an argument the Git protocol refuses, such as a path outside the repository or a branch name that starts with `-`, as `Refused` with `git.invalidArgument`, a folder outside a repository as `Refused` with `git.notRepository`, a write the module refuses, such as `git.nothingToCommit`, as `Refused`, a moved status or request as `Stale`, a denied, expired or withdrawn request as `Denied`, `Expired` or `Withdrawn`, and git or its lock out of reach as `Unavailable`.
  Any failure after a write's point of no return is `OutcomeUncertain`, keeping its module code, with `git_status` as the tool that tells the agent where things stand.
- The app binds each agent session's folder as `git.folder`, read with the Git protocol's `GitFolderBinding`, and the modules' tools that act on a repository act only in the one that holds it; a tool never takes the folder from its arguments.
