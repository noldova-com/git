# Architecture

**Scope:** The repository's modules, their packages and parts, how they build, pack and release, and the boundaries their code keeps.

## The modules

The repository holds a set of modules for apps on [Noldova Desktop](https://github.com/noldova-com/desktop), each in its own folders in `src`, as [README.md](../README.md) describes.
Today it holds two: the local Git module, its main module, in `src/noldova.git`, and the GitHub module in `src/noldova.git.github`, each with its protocol and window part in sibling folders named after it, such as `src/noldova.git.protocol` and `src/noldova.git.window`.
Beside them is the hosting protocol, `src/noldova.git.hosting.protocol`, a package that every host module implements and that isn't a module itself.
A host module added later, for another service, joins them as folders beside them, a module a person can turn off.
A host module depends on the local module and the hosting protocol, never on another host.

The repository automation reads the modules from one list, which `scripts/models/repository-module.ts` builds from the names in `scripts/resources.ts`: each module's name, which is its folder under `src`, and its package name, from which its protocol's and window part's folders and names follow, and, apart from them, the packages the modules share, by folder and package name.
The package layout, the build, the packer, the declaration check and the test type-check go through every module in the list and every shared package; the import scan takes every package whose name starts with the main module's package name and a dot, `@noldova/git.`, as one of the repository's own.

## The package

Each module ships as three packages, and the hosting protocol as one, all at the local Git module's version, with every pin exact and every peer a range, as below; a peer on another of the organization's packages runs from a version it was built and tested with to the next minor below 1.0, as the organization's TypeScript standard (`standards/stacks/TYPESCRIPT.md`, "Dependencies") says.
Noldova Desktop's catalog still requires an exact peer on a package outside its shared packages, so an app that includes the GitHub module builds only with the Noldova Desktop release that accepts a ranged peer, noldova-com/desktop#111.
Each module accepts a range of Noldova Desktop versions, its `module.json`'s `noldovaDesktop`, `>=0.0.3 <0.1.0`, as Noldova Desktop's `documents/MODULES.md` ("Noldova Desktop versions") says: from the version it builds and tests against, the root `package.json`'s exact pin, to the next minor below 1.0, or the next major from 1.0.
  0.0.1 is the lowest since it is the first Noldova Desktop published on npm, as the `@noldova/desktop.*` packages.
Its package's peers on Noldova Desktop's packages take that range, and context's a range of the same form; the window packages' peers are written at packing: context's packages as each window project's `peerDependencies` declares them, `>=0.0.7 <0.1.0`, since each of context's packages pins its siblings exactly and an exact dependency would install a second copy; Noldova Desktop's packages taking `noldovaDesktop`; the kit the range from its pin to the next minor; Angular's the range from its pin to the next major, as that document's "Angular versions" says, and the repository's own packages the range from the module's version to the next minor, such as `>=0.0.1 <0.1.0`, which the shared pipelines' archive step requires of a package that takes its siblings as peers.

Each part, and the hosting protocol, keeps its source in `src/` and its tests in `tests/`, mirroring `src/`, and declares its entry point `src/api/index.ts` in a handwritten `src/api/index.d.ts`.
A module's parts import its protocol, and a host module's parts the hosting protocol, by package name.
Every package under `src` is one of the root's npm workspaces, so the repository has one install, the root's `package-lock.json`, whose `node_modules` links each package to its source.
Context's core package defines fixed properties on `Object`, so a second copy throws when it loads; the build checks that the install holds one, and each window part's `vitest.config.ts` has Vite pre-bundle the three context packages, so its tests load one.
The window part's own code may import them as values, such as context's `Exception` and `JsonException`: the published window packages take `@noldova/context.exceptions` and `@noldova/context.json` as peers, so an app holds one copy, and its tests pre-bundle them, so they load one too.
The Git view's branch icon is Primer Octicons' `git-branch` (MIT); the window part's `THIRD-PARTY-NOTICES.md` carries its license and ships in its package.
Each manifest exports `.ts` sources.
The build maps each export to its compiled `.js` and to the handwritten declarations beside it.

`npm run build` (`scripts/build.ts`) runs `npm ci`, with a 10-minute deadline, when there is no install or `package-lock.json` is newer than the last install's `node_modules/.package-lock.json`, then checks, with npm's own tree listing, that the repository's tree holds one copy of `@angular/cdk`, which the UI kit shares, and one of `@noldova/context.core`, which context's packages, Noldova Desktop's and the protocols share, and stops, naming each copy, when it holds more of either, or none ([TESTING.md](TESTING.md#the-pull-request-checks)). `scripts/models/single-copy-package.ts` names both packages.
The modules' packages aren't npm workspaces: the root `package.json` holds every development dependency, the window parts' Angular, interface kit and browser test packages among them.
The build then removes `_packages` and `_build/compiled` and builds each package in turn, the hosting protocol first, then each module's protocol, window part and own package: it compiles a protocol or runtime part into `_build/compiled/<folder>`, such as `_build/compiled/noldova.git.protocol`, packs the package into `_packages`, building it in `_build/packages`, and installs every archive packed so far into the repository's `node_modules` with `npm install --no-save` (`scripts/services/package-install.ts`), as an outside user installs them; each install also names the version `node_modules` holds of each `@noldova/` package the root `package.json` pins, since an install otherwise takes the lockfile's version back, so a build after the Module range workflow's install keeps the newest Noldova Desktop in range and the versions it pins.
So each part, each window part's build and every test import the packed packages built before them, never their sources, and no configuration maps a package's name to a path.
Each manifest records the commit as its `gitHead` only when the folder is a git checkout without uncommitted changes; otherwise the build says why it records none.
A window part's build imports its module's protocol, the hosting protocol, and the protocol and window part of each module its module depends on (`RepositoryModule`'s `dependencies`: the GitHub module's are the Git module's) as installed from their archives, and takes the window package's dependencies and peers from what the compiled part's scripts and declarations import, at the versions the window part's `package.json` pins, and the repository's own packages at the module's version. It refuses to pack a part that imports a package the manifest doesn't pin. The packages of a module its module depends on are peers from the module's version to the next minor, optional as the app's are, not dependencies, so an app holds one Git window part, whose host rows the Git view reads.

`.github/workflows/release-npm.yml` releases the packages to npm through the organization's shared npm release, v2.34.0, with npm's trusted publishing and provenance, so no token is stored: each package's trusted publisher on npm is this repository's `release-npm.yml` in the `release` environment.
A member starts it by hand with a version and a commit on main, and the `release` environment's reviewer approves the publication.
The pull request that changes the version writes that version's section in [CHANGELOG.md](../CHANGELOG.md), from the pull requests merged since the previous version, and no other pull request edits the file.
A release never deletes a published version.
After the release, its dependents job calls the organization's shared `update-dependents.yml`, v2.34.0, with the version and the commit, in the `version-updates` environment, which holds the version-updates App's key and deploys from `main` only; each repository the App's installation includes that pins this module's packages exactly at an older version, such as the app, gets a pull request that moves the pins and refreshes its lock files, as the shared workflow's README says.
The shared release reads the version from `version.json`, checks that the commit is on main and holds that version, and tags the commit first; it then runs `npm ci` and `npm run build`, checks the archives in `_packages` against the build's `--list-copies`, and publishes them.
A build or publish that fails keeps its tag, so the same version can be released again from the same commit, but a fixed commit needs a new version.
`npm run build` refuses to pack when `version.json`, the root `package.json` or another module's `module.json` holds a version other than the local module's `module.json`, so a version change moves them all, with every package's manifest.

The build type-checks them against `@types/node` 26 and the tests run on Node 26.13.1, so a call only Node 26 has passes both, and a review keeps it out.

The local module's runtime part reads and writes a repository through the person's own `git`, and the agent tools reach it through Noldova Desktop's permission requests.
Its window part shows the Git view of one folder, which the app provides through `GitFolder.provide`; the view refuses a folder that isn't an absolute path of at most 4096 characters and logs why.
The view reads the folder's status, branches and diffs through the runtime's `git.*` methods, watches the folder while it shows it and reads the status again on each `git.changed` event; a watch the runtime refuses shows a notice that changes aren't followed, with Check again to watch and read again; and sends every write with the status's fingerprint; a write the runtime refuses as `Stale` reads the status again and keeps what the person typed.
The view shows as a failure only the window's own failures of a request, a `WindowException`, and an answer it can't read; any other error, a defect of the view's own, is passed on to Angular's `ErrorHandler`.
It shows the branch card with Push or Publish branch, a host row, a merge or rebase in progress, the Conflicts, Staged and Changes groups with each file's diff inline under its row, and the commit card; `NotRepository`, a folder the person's account may not read (`FolderUnreadable`), git missing or too old, and a folder the app's folder provider can't read each show their own empty state, the last with the provider's message.
A host module adds its row through `GitHostRows.provide`: the first row whose `claims` accepts the remote renders its component with the folder, branch, head and remote, and a remote no row claims shows one plain line naming it.
Pull sits beside Push whenever the branch has an upstream, since a pull fetches first; it sends `git.pull`, which fast-forwards only and refuses a branch with no upstream or a gone one, a merge or conflicts in progress, and a divergence, and the view shows each refusal's message as an alert.
Pull's tooltip names the repository's hooks that a pull runs, which `git.pullHooks` reads when the pointer or focus first reaches the button in a folder; until then it says a pull fetches and fast-forwards only, running the repository's hooks, and once read it names them.
The GitHub module's runtime part signs in to GitHub with GitHub's device flow and reads its issues, pull requests and checks; its window part shows the sign-in and, in the Git view's host row, a branch's pull request and its checks.
Each arrives in its own pull request.

## The local runtime part

The runtime part runs the person's own `git` through Noldova Desktop's `startProcessAsync`, never a shell, with the C locale, no prompt, no pager and `GIT_LITERAL_PATHSPECS=1`, so a path is never read as a pattern, and with the person's `HOME`, or on Windows `HOMEDRIVE` and `HOMEPATH`, so git finds their own configuration; every run adds `-c core.fsmonitor=false`, so a command that a repository's own configuration names as its fsmonitor never runs from the module's reads, polls or writes, every read adds `--no-optional-locks`, so it never takes a lock another git client needs, and every path comes after `--`.
Before each status and diff, the runtime reads which filter drivers the repository's own configuration, `local` or `worktree` scope or a file it includes, gives a `clean` or `process` command, and switches each off for that read with `-c filter.<driver>.clean=`, `-c filter.<driver>.process=` and `-c filter.<driver>.required=false`, so a status or diff never runs a command that came with the repository.
It reads the same of each checked-out submodule's own configuration, at any depth, since git's status runs inside each submodule with that submodule's configuration, and git passes the options on to it; a repository with more than 256 checked-out submodules isn't read, as `Unavailable`. A driver whose name holds `=` can't be named in an option, so the read fails as `Unavailable`.
The person's own system and global filters still run, as for their own `git status`: Git LFS, which `git lfs install` sets up in the global configuration, works as before; an LFS set up only in the repository's configuration is switched off, so a tracked LFS file that git hashes again shows as changed, against its pointer.
A write runs the repository's filters as the person's own git does, a known limit: a person's click is their own `git add` or `git switch`, and switching a filter off would store or check out something else, such as an LFS file's whole content instead of its pointer. An agent's stage or switch names, in its request, each driver the repository's own configuration gives a command that write runs: `clean` or `process` for a stage, which then asks at low risk, and `smudge` or `process` for a switch. When `submodule.recurse` is set, a switch checks out each checked-out submodule too, so its request also names each of those submodules' hooks, with the submodule's path, and the `smudge` or `process` drivers its own configuration names, at any depth, found by the same submodule walk as the reads.
The diffs pass `--no-textconv` and `--no-ext-diff`, so a textconv or external diff command never runs.
Each run has an output limit and a time limit, and a run past its time limit is stopped.
A run cancelled or past its time limit fails as soon as its program has exited, without waiting for the rest of its output: a process the program started that outlived it, such as one that left its process tree, may still hold the output open, and the run never waits on it.
A read first checks, once while it passes, that `git version` is 2.39 or later, the oldest whose output the module reads; an older git's failure names its version, such as `2.34.1`, in `gitVersion`.

Each method takes a folder, finds the repository's top, git folder and common git folder with `git rev-parse`, and reads one read at a time per repository.
`git.diff` answers the diff of the worktree, the staged changes or a range of two revisions, which come after `--end-of-options`, with each file's hunks and lines up to 1 MiB a file and 4 MiB in all, and the worktree's untracked files after its tracked ones, at most 1,000.
`git.branches` answers the local branches in git's order, the branch HEAD names, also before its first commit and `null` on a detached HEAD, the remotes' names, and the remotes' branches as `<remote>/<branch>` without each remote's `HEAD`.
`git.log` answers HEAD's newest commits, up to the request's limit and none before the first commit, each with its id, parents, author's name, authored time with its offset and subject, never the author's email; a name or subject has each control character replaced and is cut to 1,000 characters, and `truncated` says HEAD has more.
`git.worktrees` answers the repository's worktrees from `git worktree list --porcelain -z`, the main one first, each with its folder as git prints it, the commit and branch it has checked out, `null` before the first commit, on a detached HEAD or for a bare repository, and whether it's locked or prunable; a list past 4 MiB fails as `Unavailable`.
`git.pullHooks` answers which of the hooks a pull runs, `post-merge`, `post-index-change` and `reference-transaction` in that order, git would run from the folder it takes hooks from, `core.hooksPath` too, as the commit request names its hooks; it fails as `Unavailable` when git can't name that folder or a hook's file can't be read, and the Git view's tooltip then keeps saying a pull runs the repository's hooks.
`git.watch` and `git.unwatch` count each window's watches of each folder; while any window watches a folder of a repository, the runtime watches the repository's HEAD, index, branches and packed refs, polls every 5 seconds, and answers `git.watch` once the watch has started: after writing an empty `noldova-watch-<random>` file into the git folder and a `noldova-watch-<random>.lock` into `refs/heads`, it waits until each folder's watcher reports that file, then removes it; a file not reported within 5 seconds counts the watch as started anyway and is logged with its folder, and after a 200 ms debounce reads the status, and when its fingerprint moved it sends `git.changed` with the watched folder to each window watching one of the repository's folders, the first read included. A closed window or connection drops its watches, and an unwatch or a closure that comes while a watch's repository is still being read cancels that watch.
`git.status` reads:

- the branch, HEAD, upstream and entries from `git status --porcelain=v2 -z`, at most 10,000 entries, with every option the person's configuration could change fixed;
- each changed side's line counts from `git diff --numstat -z`, the index against HEAD with renames and the worktree against the index without, a binary file's as none; an untracked text file counts its own lines, up to 1 MiB a file and 32 MiB in all, and a binary file, a path that isn't UTF-8 or a file past the limits counts none;
- the merge, rebase, cherry-pick or revert in progress from the files git keeps in the worktree's git folder, where a rebase wins over the commit it picks and a mailbox apply shows none;
- the remote from `git config`: the one the branch's configuration names, else the repository's only remote, with its host and path read from an HTTPS or SSH URL or an scp-style address, never the URL itself or the name, password, token or port in it; a local path or `file://` remote names no host or path, and a path with an empty, `.` or `..` segment names none;
- the fingerprint, a SHA-256 of the status's output, the index file's size and times, and each listed path's size, times and mode, so it moves when HEAD, the index or a changed file does.

A failure answers with Noldova Desktop's code and a `GitFailure` in the details: `Stale` as `Conflict`, `NotRepository` as `NotFound`, `Unavailable`, also a missing or older git and a folder the person's account may not read, as `Unavailable`, `Refused`, also a request the protocol refuses, as `InvalidParams`, and every other as `Internal`.
No message holds a URL's name, password or token, also when git prints one.

The runtime part also publishes `git.repositories`, a `GitRepositories` from the Git protocol, for the modules that declare `git` among their dependencies, such as a host module's agent tools.
It only reads: `readStatusAsync` reads a folder's status as `git.status` does, with the same folder check, the same queue per repository and fsmonitor off, and rejects with the same failures; `readRemoteAsync` reads one remote by its name, such as `origin`, whatever remote the branch works with, the same way.

### Worktrees

`WorktreeService` makes and removes a worktree for an app's opaque key, which never appears in a path or a branch name. The runtime part declares its `worktrees` table's migration, `create-worktrees`, and runs `reconcileAsync` at activation, which with no records runs nothing. Since the part declares a migration, Noldova Desktop opens and migrates the module's database before activation, and a database that can't open or migrate fails the whole Git module, its reads, writes and tools too. The reconcile runs before the module's methods register, so once records exist, each record's and each recorded repository's git runs delay them. No method, tool or published service reaches the rest yet, and each removal brings its caller's permission gate.

- `createWorktreeAsync(key, options)` runs `git worktree add --lock --reason <reason> -b <branch> <path> <base>`, with the path under the module's work folder, outside the repository, the base HEAD and the branch `noldova/<id>` unless the options name them, so the worktree is locked in the same step; the module knows its own lock by the reason. The same key always gives the same record, and a key whose worktree is in another repository is refused. `git worktree add` runs the repository's `post-checkout` hook, as checking out a branch does.
- A record is written to the module's `worktrees` table as pending before `git worktree add` runs, and marked ready once it succeeds, so an interrupted create leaves a pending record the module clears later.
- `removeWorktreeAsync(key, options)` asks the options' permission gate first, with `git.removeWorktree`, when the worktree has changes: the tracked and untracked paths `git status` reports, bound by a digest of the status and each changed file's content, so a change after the answer keeps the worktree as `Stale`. Ignored files don't count, and go with the worktree. It then unlocks and removes it; the branch stays unless the call asks to delete it, and `git branch -d` keeping it fails as `BranchUnmerged`. A worktree another tool locked is never touched, as `LockedElsewhere`.
- The module never runs `git worktree prune`, which can't target one entry. It clears its own stale entry, a pending one or one whose folder is gone, by unlocking it and running `git worktree remove --force <path>` on that entry alone, then drops the record; the next create for the key makes a fresh worktree on a new path and branch.
- `reconcileAsync()` clears each stale record as above, then reads each recorded repository's `git worktree list --porcelain -z` and logs, without touching it, each worktree it didn't make.
- `statusAsync(key)` and `diffAsync(key, scope, paths)` read the key's worktree as `git.status` and `git.diff` do.

### Writes

Each write method takes a folder and `basedOn`, the fingerprint of the status the person saw, and answers `null`; the window reads the status again on the `git.changed` that follows.
They are the person's own clicks: each answers `Unauthorized` to any caller but the app's main process acting for a window, before it reads its parameters, and never asks; an agent writes only through its tools, which raise Noldova Desktop's permission requests, as [SECURITY-MODEL.md](SECURITY-MODEL.md) says.
`WriteRunner` runs each write: it reads the status and refuses one whose fingerprint moved as `Stale`, lets the write refuse what the status can't take, asks an agent's call the write's request, and then, one write at a time per repository, reads the status and the request again and runs the write only when both are unchanged; an agent's request is read again even when it asked nothing, so a hook or filter added while the write waited is `Stale` rather than run without an ask.
A write cancelled or past its time limit after git started fails as `OutcomeUnknown`, and the repository's watch refreshes after every write that ran.

| Method | What runs | An agent's request |
|---|---|---|
| `git.stage` | `git add --all -- <paths>`, a deletion too, in runs that fit a command line | None, since the person undoes it by unstaging, unless the repository's `post-index-change` hook would run, or its own configuration names a `clean` or `process` filter: then low risk, with the paths, the hook and the filters |
| `git.unstage` | `git restore --staged -- <paths>`, or before the first commit `git rm --cached -r --quiet --force -- <paths>`, keeping the worktree | None, unless the repository's `post-index-change` hook would run: then low risk, with the paths and the hook |
| `git.createBranch` | `git switch --create <name>` at the current commit; a branch an agent's session made counts as that session's only when no remote has a branch of that name | None, unless a `post-checkout`, `post-index-change` or `reference-transaction` hook would run: then low risk, with the hooks |
| `git.switchBranch` | `git switch <name>`, refused during a merge, rebase, cherry-pick or revert; a switch git refuses names the files in the way as `ChangesInTheWay`, and a branch another worktree has as `BranchCheckedOut` | Medium risk: from and to, how many unstaged changes stay, the hooks that will run, and the `smudge` or `process` filters the repository's own configuration names, and with `submodule.recurse` each checked-out submodule's filters and the hooks that move it, `post-index-change` and `reference-transaction`, with its path, since a switch moves a submodule by read-tree and update-ref, not a checkout; "Always allow" holds for the repository |
| `git.commit` | `git commit --quiet --cleanup=whitespace --message=<message>`, refused with nothing staged or with conflicts left; never amends | Medium risk: the message, the staged files, the author from the person's settings and the hooks that will run; "Always allow" holds for the repository |
| `git.push` | `git push --porcelain --no-follow-tags --recurse-submodules=no -- <remote> <commit>:refs/heads/<target>`, the commit being the branch's as the status read it: the current branch to its upstream on the remote it works with, or published under its own name, and then set as its upstream with `git config`; refused on a detached HEAD, with nothing to push, or behind its upstream | Asks at High risk, in every mode, or at Medium for the session's own branch below, which a host's unrestricted mode pushes without a card: the remote's push URL without its name or password, the branch, the commits it sends, up to 100 shown, and the hooks that will run; "Always allow" only for a branch the session made under the same name that isn't the remote's default branch, and that request's subject names the session |
| `git.pull` | `git pull --ff-only --no-rebase --no-autostash --quiet`: fast-forwards the current branch to its upstream; refused before it runs on a detached HEAD, with no upstream or a gone one as `NoUpstream`, during a merge or other operation or with conflicts as `Conflict`, and when the branch is both ahead and behind as `Diverged`; a pull whose own fetch finds a divergence fails as `Diverged`, and one that would overwrite an uncommitted change as `ChangesInTheWay`, naming up to ten of the files, with the tree unchanged; an uncommitted change the pull doesn't touch stays. A known limit: a Pull click is the person's own `git pull`, so the repository's hooks (`post-merge`, `post-index-change`, `reference-transaction`), its fetch settings such as `core.sshCommand` and `credential.helper`, and its smudge and process filters run, as they do in a terminal | Medium risk: the upstream, the branch, the hooks that will run and the smudge or process filters its checkout will run, and with `submodule.recurse` each checked-out submodule's filters and checkout hooks, `post-checkout`, `post-index-change` and `reference-transaction`, with its path, since the pull's submodule update checks each one out; "Always allow" holds for the repository |

No write forces, resets or rewrites history, and the module builds every refspec from the status's commit and the checked branch name, so a push never sends a commit that reached the branch after the request was shown.
Each card names the repository's hooks the write will run, from the folder git takes them from: a click or an allowed write is the person's own git command, as [SECURITY-MODEL.md](SECURITY-MODEL.md) says.
A push the remote refuses fails as `PushRejected`, an unknown host key as `HostKeyUnknown`, a refused SSH key as `KeyRefused`, and a remote that asks for a name or password Git can't answer without a terminal as `CredentialsNeeded`; each carries git's output as untrusted text.
A request that can't fit Noldova Desktop's limits, such as a commit of more staged files than its details hold, is refused before it is raised, and a title past 200 characters is cut.

### Platform and git details

- Each git run gets `HOME`, or on Windows `HOMEDRIVE` and `HOMEPATH`, so git finds the person's own configuration, such as their identity, as their terminal's git does; Noldova Desktop passes only `USERPROFILE` on Windows, which not every Git for Windows reads as the home when `HOME` isn't set.
- A write that names paths splits them into runs that each fit one command line, since Windows takes at most 32,767 characters in one, with room for git's own arguments and each path's quotes.
- A hook counts as one git would run when it is a regular file that is executable, or, on Windows, where files carry no executable bit, one that starts as a script (`#!`) or a program (`MZ`), as Git for Windows tells them; the rule reads the starts each platform accepts, none outside Windows, with no branch on the platform, and each target's tests check its own platform's rule.
- The changes digest binds the whole status, which holds the index's object ids and modes, and the content of each changed path; it reads at most 1 GiB of changed content within 60 s, so a huge or slow file fails the request clearly instead of holding it.
- The change monitor watches the worktree's `HEAD` and index, the branches directly under `refs/heads` and `packed-refs`, each folder without recursion; file edits and branches in nested folders, such as `feature/x`, are found by the poll while the pane is visible, and when it becomes visible.
  When git's folders can't be watched, the monitor logs why and polls the worktree every 5 seconds for as long as it is watched, visible or not.
  A cookie the monitor can't write, because the folder is read-only, gone or denied, is logged and the watch counts as started at the 5-second mark; on start the monitor removes only `noldova-watch-*` files an earlier run left in the git folder and `noldova-watch-*.lock` in `refs/heads`, never another live watch's cookie.
- A conflict that git combines has a raw entry starting with `::` in `git diff -z --raw --patch`, and its `diff --cc` patch is left out of the diff.

## Signing in to GitHub

The GitHub module's runtime part signs in with GitHub's device flow, as Noldova's GitHub app, whose client id is public and which has no client secret.
It asks for the `repo` scope, and the sign-in's state is a `HostSignIn`: signed out, with the failure that ended the last sign-in if one did; waiting, with the code the person enters at GitHub's address; or signed in, with the account's login, name, avatar and the scopes GitHub granted.
The account's avatar reaches a window only as a base64 data address, or null, never as GitHub's address for it: once GitHub answers the token's account, the part keeps and shows the account at once, then reads its avatar the same way and with the same reader as a reference author's avatar, below, and shows the account again with it, unless the sign-in changed meanwhile.

| Member | What it does |
|---|---|
| `git-github.readSignIn` | Answers the sign-in as it is. |
| `git-github.startSignIn` | Asks GitHub for a code and answers the waiting sign-in; while one waits or is signed in, it answers that one. |
| `git-github.cancelSignIn` | Stops a waiting sign-in, which ends signed out with no failure. |
| `git-github.signOut` | Stops a waiting sign-in, or forgets the kept token, and answers the signed-out state. |
| `git-github.signInChanged` | The event that carries each new state. |

While a sign-in waits, the runtime part polls GitHub at the interval GitHub names, at least a second and five seconds when GitHub names none, waiting longer whenever GitHub asks it to slow down: at the interval GitHub then names, or five seconds more.
It refuses a code whose expiry isn't between a second and an hour.
A sign-in ends signed out with `Expired` when the code expires, `Denied` when the person refuses it, `Unreachable` when GitHub can't be reached or doesn't answer in 30 seconds, `Refused` when GitHub answers something the part can't use, and `Unkept` when the token can't be kept; a sign-out whose token can't be removed from the secrets ends signed out with `Unforgotten`, since a later start may restore it.
Only the secrets' own failures, a `MethodFailureException`, count as `Unkept`, `Unforgotten` or an unreadable kept sign-in; any other failure is passed on as it is, to the caller or the log's unexpected-failure line.

The token never leaves the main process: the window parts see only the account.
One other module can read it: the runtime part publishes `git-github.access`, an `IGitHubAccess`, exported from `@noldova/git.github/runtime` and `@noldova/git.github.protocol`, whose `accessAsync(signal)` answers the held token with the account's login, as a `GitHubAccessGrant`, or why there is none, as a `GitHubAccessRefusal`: "Sign in to GitHub in Settings, GitHub." signed out, a sentence on the kept sign-in that Noldova Desktop couldn't read, or one on entering the code while a sign-in waits; an aborted signal rejects with its reason.
Only a module that names `git-github` as a dependency or an optional dependency can find it, as Noldova Desktop's services go.
An app's module that names `git-github` as an optional dependency can read it each time it passes GitHub's own MCP server to a turn, so signing out stops the next turn's token; nothing logs it.
It is kept with its account, without the avatar, in Noldova Desktop's module secrets as `git-github.signIn`, encrypted for this computer only; a sign-in kept by an earlier version, with the avatar's address, still restores, with no avatar.
On activation the part shows the kept account at once, with no avatar, and then asks GitHub for the token's account and its avatar: an answer replaces it, a token GitHub no longer accepts is forgotten and ends signed out with `Revoked`, and a token GitHub can't check now stays.
While the app's main process isn't connected yet, the part reads the kept sign-in again once the app's windows change.
Signing out forgets the token on this computer only; the person withdraws Noldova's access on GitHub's page for the app, which `GitHubNames.manageAccessUrl` names.
Changing which scopes it asks for, where the token is kept or what reaches the windows is a risky change, as the repository's `AGENTS.md` says.

The module declares its own Settings page, `git-github.account` titled GitHub, in `settings.json`'s `pages` and `module.json`'s `contributes.settingsPages`, and its window part registers it on activation with `GitHubSignInComponent`, `nol-git-github-sign-in`, as its component: the Account section, under the page's title, that signs in, shows the code, the account and a failure, and signs out.
It reads the sign-in when it opens and follows `git-github.signInChanged` until it closes.
Signed out, it says what signing in brings, or why the last sign-in ended, and offers the sign-in.
While a sign-in waits, it shows the code, copies it and opens GitHub's page for it, offers to copy the code and to copy it and open the page again, and counts down to the code's expiry each second.
The page opens where the Links setting says, like every link; in the app's Browser its tab covers Settings, so the code is on the clipboard to paste, and the note says so only when the clipboard took it.
Signed in, it shows the account's login beside its avatar, or its initial when it has none, and whether it reaches the person's repositories, and offers to sign out or to open GitHub's page for the app's access.
It holds its sign-in, cancel and sign-out buttons while a request is out.
A request that fails logs why and shows a banner, "GitHub's sign-in didn't answer.", which says to try again; when the first read fails, the page shows only that banner under its title, with Try again, which reads the sign-in again.
A page it can't open, GitHub's page for the code or for the app's access, logs why and shows the banner "The page couldn't be opened." instead.
The banner clears at the next request and when the sign-in's state changes; a sign-in event in the same state, such as a late Waiting or an avatar arriving, leaves it, so a late event can't wipe a fresh notice.
The window part gives Settings search the page's rows with `setSettingsRows`, so a search finds them before the page opens.
On activation it gives the signed-out rows, then reads the sign-in and follows `git-github.signInChanged` until it deactivates, giving the rows of what the page shows.
The rows are Account, always, whose description is what signing in brings, the code's note or the account's access; Sign in to GitHub while signed out; and Sign out and Manage access on GitHub while signed in.
Their ids are `git-github.account`, `git-github.signIn`, `git-github.signOut` and `git-github.manageAccess`, and the page marks each row's element with its id in `data-setting`: Account on its title and what follows it, the note, the failure or the account, which hold no control, and each other row on a holder of its own button, so Settings, which focuses the first control of the row it opens at, focuses that row's button and nothing when it opens at Account.
A sign-in read that answers after a change event arrived is dropped, since its answer is older than the event's.
A read that fails keeps the signed-out rows, and a read that answers after the part deactivated gives none.

On activation the window part gives the Git view its host row through `GitHostRows.provide`, for remotes on github.com, and withdraws it on deactivation.
The row, `GitHubHostRowComponent`, reads the sign-in and follows `git-github.signInChanged`; signed in, it reads `git-github.readBranchPullRequest` for the remote's host and path, the branch and HEAD, and reads again whenever one of them changes, dropping an answer or failure for a branch it has left.
It shows the pull request's state icon in GitHub's look, its number and title, which open it on GitHub as its open button does, and its checks worst first, failed then running, queued, passed and skipped, each with its state's Octicon and label; a check's name opens its run.
A title or name the row cuts off is marked `data-truncates`, as the kit does, and shows in full in the kit's tooltip only while it is cut.
A branch with no pull request, or a detached HEAD, shows "No pull request for this branch".
Signed out, it offers the sign-in, then shows the code with Copy code and Cancel, copies it and opens GitHub's page for it; while GitHub doesn't answer, it says so and offers Try again.
A page the row can't open, GitHub's page for the code during a sign-in, a pull request or a check's run, logs why and shows the notice "The page couldn't be opened" under the row, with Open the page again, which opens that page again, so beside the device code the person still reaches GitHub's page when the first opening failed.
The notice clears at the next opening and when the sign-in's state changes; as on the sign-in page, an event in the same state leaves it.
The GitHub window takes `@noldova/git.window` from the root's install, where the build installs the Git window's packed archive before it compiles the GitHub window, so its compile and its tests use the real `GitHostRows` as an app gets it.

## Reading GitHub

The GitHub module's runtime part reads issues, pull requests and checks, and opens pull requests, under the person's sign-in, with the hosting protocol's models.

| Member | What it does |
|---|---|
| `git-github.readReference` | Takes a `HostReference` and answers its issue or pull request as a `HostItem`, or null, with the author's avatar as a data address. |
| `git-github.readBranchPullRequest` | Takes a `BranchQuery`, with the remote's host and `owner/repository` path as the Git module reads them, and answers a `BranchPullRequest`: the branch's newest pull request in the repository, and the check runs of the query's head commit, or of the pull request's head when the query names none. |
| `git-github.createPullRequest` | Takes a `PullRequestDraft`, opens the pull request and answers it as a `HostItem`. |

Signed out, for a reference to another host module or a repository off github.com, or for what GitHub can't show the sign-in, a read answers null, or a `BranchPullRequest` with no pull request, without failing, so a link stays a plain link.
A read's answer is kept for 60 seconds; after that the part asks again with the answer's tag in `If-None-Match`, which GitHub doesn't count against the rate limit when nothing changed, and keeps the 500 answers read last, none longer than 262,144 characters, for the signed-in token only.
Signing out, or signing in as anyone, drops every kept answer, and an answer that lands after the token changed is neither kept nor answered.
A `HostItem` carries when it was opened, and when a merged pull request was merged or a closed one or an issue was closed, so an app can show either age.
Its author's avatar reaches a window only as a base64 data address, never as GitHub's address for it, since a window's content policy allows only its own and data images.
For `git-github.readReference`, and for the signed-in account, the part reads the avatar at 64 pixels from `avatars.githubusercontent.com` with no token or cookie, since avatars are public and the token goes to no host but `api.github.com`; it reads a reference author's alongside the pull request and the account's once the account is shown, gives the whole read, redirects included, five seconds, follows at most three redirects, each only on that host, cancels the body of a redirect or a refused answer, takes a PNG, JPEG, GIF or WebP image of at most 64 KiB, and keeps the 500 avatars read last.
An avatar it can't read, for an HTTP failure of any status, a network failure, the five-second deadline, an answer that isn't an image, an empty or oversized body, or too many or off-host redirects, leaves the author or the account without one and logs why, without failing the read; any other error is a defect of the module's own and fails the item's read.
An agent's `git_github_read` and the other reads carry no avatar.
The author's `url` is GitHub's `html_url` for them as GitHub gives it, an app's page for an app whether or not its login ends in `[bot]`, so a window links it as is rather than building it from the login; null when GitHub gives none or one that isn't an https address, which never fails the read.
The protocol refuses an owner, repository or path with a `.` or `..` name or characters outside letters, digits, `.`, `_` and `-`, and the GitHub module also refuses an owner or repository outside GitHub's own names, so a reference never steers the token to another of GitHub's addresses.
A token GitHub refuses signs out with `Revoked` and fails the call as `Unauthorized`; GitHub out of reach or refusing fails it as `Unavailable`, a used-up rate limit naming the time it resets, and a timeout as `DeadlineExceeded`.

Only a person opens a pull request: `git-github.createPullRequest` refuses as `Unauthorized` any caller but the app's main process acting for a window, which is how a click in the module's window reaches it.
No agent reaches this method: Noldova Desktop raises a permission request only for a tool call, so an agent's way to a pull request is a tool that asks first.
GitHub refusing the pull request, for example because the branch already has one, fails it as `Conflict`.

The window part's `GitHubLooks` gives GitHub's look for each kind and state, so an app draws a GitHub reference chip and its card from a `HostItem`'s kind and state alone: the kind's and the state's labels in GitHub's words, the state's Octicon, and its colors and badge fill in light and dark, with GitHub's mark beside them.
Open is the ok status color, draft and not planned the muted text color, merged and a done issue GitHub's purple, #8250DF in light and #A371F7 in dark, and a closed pull request the failed status color.
The look is fixed in the module: no markup or color comes from GitHub's answers or the runtime part, and the icons are `data:` addresses an app draws as masks in the state's color, never markup it inserts.
The Octicons and their license are listed in the window part's `THIRD-PARTY-NOTICES.md`, with the check states' `check-circle-fill`, `x-circle-fill`, `dot-fill` and `clock`, which the host row draws the same way.

## Agent tools

The modules' runtime parts offer agent tools through Noldova Desktop's tool registry, which the app serves to its agents; they register each tool on activation and withdraw it on deactivation.

| Tool | Module | What it does |
|---|---|---|
| `git_status` | Git | Takes nothing and answers the bound repository's `GitStatus`. |
| `git_diff` | Git | Takes an optional `staged` and `paths`, each relative to the repository's top folder, and answers its unstaged, or staged, `GitDiff`. |
| `git_log` | Git | Takes an optional `limit`, 20 when left out and at most 500, and answers the current branch's newest commits as a `GitLog`. |
| `git_branches` | Git | Takes nothing and answers the repository's `GitBranches`, with `truncated` beside them. |
| `git_stage`, `git_unstage` | Git | Take `paths` and run `git.stage`'s or `git.unstage`'s write. |
| `git_create_branch`, `git_switch_branch` | Git | Take a branch `name` and run `git.createBranch`'s or `git.switchBranch`'s write. |
| `git_commit` | Git | Takes a `message` and runs `git.commit`'s write. |
| `git_push` | Git | Takes nothing and runs `git.push`'s write. |
| `git_pull` | Git | Takes nothing and runs `git.pull`'s write. |
| `git_github_read` | GitHub | Takes an `owner`, `repository` and `number` and answers the issue or pull request on github.com as the `HostItem`'s JSON, untrusted text from `https://github.com`. |
| `git_github_pr_checks` | GitHub | Takes nothing and answers the newest pull request from the bound folder's branch, in any state, with the checks on its head commit, as the `BranchPullRequest`'s JSON, untrusted text from `https://github.com`. |
| `git_github_pr_create` | GitHub | Takes a `title`, a `base` branch, an optional `body` and `draft`, and, once the person allows it, opens a pull request from the bound folder's branch into `base`, answering it as the `HostItem`'s JSON. |

- `git_github_read` is read-only and low risk, reaches GitHub, and has a 30 s deadline, at most 120 s.
- Its input schema allows only GitHub's own owner and repository names and a positive number, so the registry refuses any other argument as `Refused` without asking GitHub.
- Signed out, or once GitHub refuses the token, it fails as `Unavailable` with the module code `git-github.signedOut`, which tells the agent to ask the person to sign in; for what GitHub can't show the sign-in it fails as `Unavailable` with `git-github.notFound`, GitHub out of reach as `Unavailable` with `git-github.unavailable`, and a timeout as `TimedOut`; a cancelled call ends as Noldova Desktop's abort says.
- `git_github_pr_checks` is read-only and low risk, with the same deadlines; `git_github_pr_create` writes, is high risk, binds the `git.folder` resource, and has a 60 s deadline, at most 120 s, the registry's longest.
- Both read the bound folder's branch and its `origin` remote through `git.repositories`, never the remote the branch tracks, so a fork's pull request opens on the fork whatever the branch was made from: no usable `git.folder` fails as `Refused` with `git-github.noFolder`, a folder that isn't a repository as `Refused` with `git-github.notRepository`, no `origin`, or one that isn't a github.com repository, as `Refused` with `git-github.notGitHub`, a detached head as `Refused` with `git-github.detachedHead`, and Git or the Git module out of reach as `Unavailable` with `git-github.gitUnavailable`.
- `git_github_pr_create` asks the person first, every time, with a high-risk permission request whose action is `git-github.createPullRequest` and whose subject is the repository; its title names the repository and says when it is a draft, and its details show both branches and the draft flag as the module's text, and the title and the whole body as the agent's text. The body starts on its own line under its label, without trailing blank lines, and is left out when it holds nothing but white space; GitHub gets the body as given. The title's schema refuses a line break, so a title can't draw a false line on the card. It offers only to allow once and to deny, never to allow always, so no kept answer opens a pull request.
- A denial fails as `Denied`, an expired request as `Expired` and a withdrawn one as `Withdrawn`, all before anything reaches GitHub; a base branch equal to the bound branch is refused before asking. Once allowed, the call is sending: any failure from then on ends as `OutcomeUncertain`, keeping its module code, with `git_github_pr_checks` as the tool that finds out whether the pull request was opened.
- The Git module's tools act only in the repository that holds the bound folder, through the same readers, the same queue per repository and the same writers as the window's methods, and answer the repository's text as untrusted, with the origin `git:repository`: a read its `GitStatus`, `GitDiff`, `GitLog` or `GitBranches`, and a write the `GitStatus` after it, or, when that status can't be read, that the write is done and the agent should read it with `git_status`, so a write that ran is never answered as uncertain and repeated.
  A result past a tool result's size keeps as many items, entries, files, commits or branches, as fit and is marked `truncated`, and one that can't fit even so fails as `TooLarge` with `git.tooLarge`.
- The reads are read-only and low risk, with a 30 s deadline, at most 120 s.
- Each write bases itself on the status it reads first and runs through `WriteRunner` with the call as the agent's, so it asks at its writer's risk, as "Writes" says and [SECURITY-MODEL.md](SECURITY-MODEL.md) holds: stage, unstage and create a branch low, asking only when a hook would run or the hooks can't be read, switch and commit medium, pull medium and open-world, push high and open-world.
  Each takes its turn on the `git.folder` resource, marks its point of no return just before git starts, and has a 60 s deadline, at most 120 s.
- A Git tool fails with Noldova Desktop's code and the module code `git.<camelCase>` of the module's failure, with git's output as the repository's untrusted text: no usable `git.folder` as `Refused` with `git.noFolder`, though Noldova Desktop refuses a write with no `git.folder` at all before it runs, since the write takes its turn on that binding, an argument the Git protocol refuses, such as a path outside the repository or a branch name that starts with `-`, as `Refused` with `git.invalidArgument`, a folder outside a repository as `Refused` with `git.notRepository`, a write the module refuses, such as `git.nothingToCommit`, as `Refused`, a moved status or request as `Stale`, a denied, expired or withdrawn request as `Denied`, `Expired` or `Withdrawn`, and git or its lock out of reach as `Unavailable`.
  Any failure after a write's point of no return is `OutcomeUncertain`, keeping its module code, with `git_status` as the tool that tells the agent where things stand.
- The app binds each agent session's folder as `git.folder`, read with the Git protocol's `GitFolderBinding`, and the modules' tools that act on a repository act only in the one that holds it; a tool never takes the folder from its arguments.
